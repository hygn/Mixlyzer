# AGENTS: core/ (Mixlyzer)

The details of `core/`: the settings and their owner, the controls' files, the loaded track, the workflows and workers, tie-ups, playback and External Sync; the library is `core/library/AGENTS.md`'s. The root `AGENTS.md`'s rules (run, layers, owners, change guidelines) apply here too; read it first.

## Map
- `core/`: the app's features, a package each (`core/__init__.py` maps them).
  - `settings/config.py`: dataclass config schema, defaults, `load_cfg()` (`outputconfig`: the headphones' / booth's output); `settings/store.py`: `SettingsStore`, the settings' one owner, and `current()`.
  - `controls/midi.py`: a MIDI controller's mapping, the shortcuts' file convention: the shipped `assets/midi/default_midi.json` (empty) and the user's `assets/midi/midi.json` (gitignored), action id -> messages as rekordbox's CSV writes them ("900B" a note, "B000" a CC, "E000" a pitch bend), options after: H a 14-bit CC (LSB at data 1 + 32), I inverted, a relative encoding O (offset 64) / T (two's complement) / S (sign-magnitude; none: guessed per value), + / - only that direction of a relative control (`Message`). The actions (`ACTIONS`) are a DJ controller's, not the keyboard shortcuts', ids naming deck 1 and mixer channel 1 (the deck and its channel): the deck (`deck1.`) PLAY / PAUSE, CUE, track start, tempo slider / range / reset, pitch bend, the jog's mode (JOG MODE VINYL / CDJ, lit in VINYL), touch / top / side / SHIFT search, CUE CALL, JumpCUE pads and their delete, beat jump; its mixer channel (`mixer.ch1.`) the fader, trim, EQ HI / MID / LOW, COLOR (its Sound Color FX knob), CUE and the level meter; the headphones' mix and level, the master's level; the browser (BROWSE knob turned / pressed, BACK, zoom), LOAD, MASTER TEMPO, MEMORY / DELETE; the effects (`fx.`, the Effects group: each Sound Color FX's button and PARAMETER, with their lamps). Each has a kind (button, fader, knob, touch, meter): the engine's code (`code`) or the GUI's actions (`gui`: a knob's per direction), its lamp. Settings shows them all; a mapping's entries of no action (an earlier version's) are not bound and dropped at the next save. The GUI's actions go to the engine as `ACT_GUI` + their place (passed back, run as their shortcuts by `AppWindow._on_midi_events`; a knob's steps repeated). `import_rekordbox_csv` reads rekordbox's MIDI CSV: deck 1's column (a whole message or a channel offset to the input column), mixer channel 1, the global browser / headphones rows and ChannelLevel's output, the CFX knob of channel 1 (`CFXParameterCH1`: the COLOR); other decks, channels and effects are left out.
  - `controls/shortcuts.py`: the keyboard shortcuts' files: the shipped `assets/shortcuts/default_shortcuts.json` (only read; `save` refuses it) and the user's `assets/shortcuts/shortcuts.json` (gitignored; only the actions changed from the shipped keys, a missing file = the shipped keys), both action id -> key sequences in Qt's portable text.
  - `track/`: the deck's loaded track, its one owner (`core/track/__init__.py` maps it). `reanalysis.py`: an editor's partial reanalysis as it is asked and answered (`ReanalysisRequest` / `ReanalysisResult` and the kinds: the contract of the editor, its workflow and the worker process; importing it imports no analysis). `model.py`: `DataModel`, what the track is (its stored analysis, `analysis`: a `StoredAnalysis`; properties, album art, decoded audio) and its marks as edited (beats and tempo rows, keys, phrases covering the track as `analyzer.music.marks.Phrase`, JumpCUEs as `JumpCueGroup`s (the stored graph itself: each group's `JumpCue`s by point and its colour preset), CUE points as `CuePoint` (all typed and immutable, from the analysis on: an edit replaces one, `dataclasses.replace`); `beats`, `tempo_segments`, ...) with the undo history and whether they are stored (`unsaved`: the history's snapshot last saved, compared by identity, and the automatic results given since; an edit made while a save runs stays unsaved, an undo back to the saved snapshot is saved; JumpCUE letters the load had to give are unsaved from the start). Everything that changes them goes through its methods (`load`, `set_beatgrid`, `set_key_segments`, `set_phrases`, `set_jump_cues`, `set_cue_points`, `set_automatic` for a reanalysis's automatic result, `undo` / `redo`, `mark_saved(point)` with the `save_point()` taken with the edits saved, `set_decoded_duration`, `set_predecoded_audio`), each telling its own signal at once (`sig_loaded`, `sig_properties_changed`, `sig_album_art_changed`, `sig_audio_changed`, `sig_beatgrid_changed`, `sig_keys_changed`, `sig_phrases_changed`, `sig_jump_cues_changed`, `sig_cue_points_changed`, `sig_edits_changed`); `analysis` is frozen (a reanalysis's automatic results replace its fields), `properties` a read-only dict (a write raises), the marks' arrays read-only (an editor copies, changes, sets). `stored_edits()` the editor's save, a `TrackEdits`. `marks.py` the editor's forms made from the stored analysis (pure functions); `history.py` the snapshots.
  - `workflows/event_bus.py`: Qt signal hub for the app's requests and reports (the deck, the library, the workers, the settings); the loaded track's changes are the model's signals, not the bus's.
  - `workers/`: analysis, segment reanalysis, optimizer, and Rekordbox worker implementations.
  - `workflows/`: Qt-facing worker lifecycle and queue orchestration.
  - `library/`, `analysis_library/`: the library and the tracks' stored analyses, their one owner: `core/library/AGENTS.md`.
  - `tieups/domain.py`: tie-ups, their domain (`Work`, `TieUp`, the categories, roles and languages, names' keys and readings, the comment's suffix; their tables and SQL are `core.library.tieups`', each function named here run through the owner's jobs): the works a track is used in, owned by the track as everything else is (the library shows its rows: no song entity, nothing shared behind the scenes). A work (the IP a song comes from: what matters, its role a bonus): anime, game, drama, movie, media mix, 2D idol, commercial, other; its names after AniDB's title types and MusicBrainz's aliases: official titles, each language's first its primary (the library and the comment show the title in the UI's language and region, else in its language, else the first), and names never shown (synonym, short, search hint), all read by `core.search.reading` so a work is found in any script; every name's language an `ll-RR` tag (ISO 639-1 + ISO 3166-1 alpha-2: `ko-KR`, `ja-JP`, `en-US`; a romanization is a synonym under the original language; `is_lang`, the table's CHECK); its web references. A tie-up: the track, the work, the role (not specified: the work alone, shown as its title; opening, ending, insert, theme, character / unit / image song, title / login screen, main screen, event, BGM, other), a number (OP2) and a detail (episodes, the song's version); one per (track, work, role, number). Tagged automatically only where the user acts: a new track's first analysis takes its versions' tie-ups (`core.library.tieups.match_new_track`, in `jobs.store_analysis`: its Variants group's, each once; never a reanalysis or Index Now), and a tie-up added in the Tie-ups tab goes to the track's versions where they lack it when `libconfig.tieup_to_versions` says so (Settings > Library, on by default; `save_tieup`'s versions; edits and removals stay on the track). A work found again (a web lookup's) is the library's row it is (`find_work`: the same Wikidata item or Wikipedia page among its references, else an official title or synonym in common, compared by `name_key`: NFKC, variant characters as their standard ones (髙 / 高, 﨑 / 崎: `reading.fold_variants`; old forms such as 澤 kept), case folded, letters and digits in their own script, no reading, so two Han spellings read alike stay two works; abbreviations and search hints never; two works matching: a new one, left to the user to merge); `add_names` adds names and references, never overwrites, the category kept. A web tie-up adds no "not specified" where the track has the work, and a role found replaces the work's "not specified" in its place (`core.library.tieups.add_found`). A server for shared tie-ups is left for later: nothing here is made for one (the ids are the library's own UUIDv4s).
  - `tieups/web.py`: tie-ups looked up on Wikimedia (`libconfig.tieup_web_search`, off by default: it sends a track's title and artist; and the Tie-ups tab's Find on the Web): looked up by several names and searches (`queries`: the title, without a "feat. …" or a version note at its end ("(TV size)", "(Club remix)", "(ふたりば～じょん)"), without a subtitle after 〜 / ~; the artists the artist field and the title credit, "A from B" / "A feat. B" split, a character's credit "Unit[キャラA(CV.声優A)&…]" giving the unit, the voice actors, the characters, a parenthesis without "CV" its voice actor or members ("シャロ(内田真礼)", "ゆいかおり(小倉唯&石原夏織)"; a version note in it left out), "Unit(キャラ…)/CV:声優…" its voice actors; the same names are the Related Tracks' Same Artist, `core.search.related.artist_keys`); the song's own Japanese Wikipedia page first (`曲名`, `曲名 (曲)`, `曲名 (シングル)`, `曲名 (歌手の曲)`; read whole), else the searches in turn (each name quoted, with each artist, the album's name), each one's first pages read where they name an artist (its letters or sounds), until two pages agree on a work or 8 are read; the song found in a page's lines as the library's search finds a title (`found_in`: `reading.find`, one sound off per 5 letters), each with the lines describing it (`_entry`: a table row's cells, a list item's or a label's deeper lines, a heading's paragraph); a tie-up read as Japanese articles write it (`mentions`: (medium)「work」 … role(number), and on the song's own page a work named by its medium alone, with no role (メディアミックスプロジェクト『作品』にて誕生); a work inside the work (作中作『…』) not one; or a work's page, or its discography page (`listed_work`: 作品のディスコグラフィ), listing the song: that work, under the role before the song, in its description or in the heading / label above, else not specified; a page read as a work only where it is one by its Wikipedia categories); a work's page by its categories (`page_category`: the works' indexes `アニメ作品 あ` / `漫画作品 ゆ`, a year's `2019年のコンピュータゲーム`, a company's `…のアニメ作品`, `…ゲームソフト`, or its franchise's own category on a page no person's, group's or record's; a 2D idol where it or its categories' categories are `アイドルを題材とした…`, or a fictional idol group, `架空の音楽グループ` with idols in its name or categories; a fictional band without idols is its work's; or a franchise's virtual idol project, `バーチャルアイドル` / `バーチャルYouTuber` in a category whose own are a work's (vα-liv in アイドルマスター, アイカツアカデミー! in アイカツ!), not a page of the franchise's concerts, companies, characters or lists (`_NOT_PROJECT`: checked on the 85 members of Category:バーチャルアイドル and Category:アイドルマスター, リッジレーサー's 永瀬麗子 the character left out)); the category a 2D idol, else the medium, else the work's Wikidata class, else its page's categories; an episode range in the same sentence its detail; a work is its page (the names linking one page are one work); the work's names in other languages from its Wikidata item's labels and aliases (codes mapped to `ll-RR`, others left out), its pages as references. Sure (written without asking: `tag_track`; the one Find on the Web checks: both alike), decided by the work, of the works whose pages are works': on the song's own page, the work it names most, with its first role by OP, ED, theme, insert, ...; from the searches, the work most pages name, with the role more of them name than any other, else not specified (ties: the category by anime, game, 2D idol, ..., then the one found first; whatever was found gives a tag: a little wrong now and then is better than none). The others are suggestions only. The answers' cache key carries `RULES` (raise it when the reading or the pick changes). One request at a time, a second apart, Wikimedia's User-Agent and maxlag (`shared()`); answers kept 30 days in `cache/tieup_web.db` (gitignored). `core/workflows/tieup_web.py` runs them off the GUI thread (a new track the analysis's versions gave none, `features_properties["new_track"]` / `["tieups"]`; each a task of the Workers window's Tie-up Lookup tab: `queued` / `started` / `done`, made tasks by `AppWindow`).
  - `playback/external_sync.py`: External Sync (another program's deck followed, received as OSC) / transport lockout; `osc.py` the strict OSC 1.0 decoder it reads with.
  - `playback/player.py`, `views/timeline.py`, `workflows/taskmanager.py`: playback, viewport timeline, worker/task UI state. The deck (the native engine's `src/deck.rs`, or `audioengine/python/deck.py` on the Python engine) takes requests (`EventBus.sig_deck_action`: `audioengine.controls.ACT_*` codes pressed / let go; `sig_tempo_requested` (the range is the deck's `ACT_TEMPO_RANGE`), `sig_volume_requested`, `sig_jump_to_requested`, `sig_call_requested`, `sig_deck_marks`) and reports what it is (`DeckReport` through `sig_deck_state`, `sig_playback_status`, `sig_tempo_factor_changed`): the GUI shows the report only, never a transport state it computed (playing, tempo, tempo range, volume, the cue point, the PLAY / CUE lamps, the armed JumpCUE). The native feeder's report waits for every command sent to be taken (`cmd_done`), so a request on its way is not shown undone. `PlayerController` starts the audio engine of Settings > Audio's Audio engine (`playbackconfig.audio_engine`, applied at the next start: "native", the default, falls back to the Python engine where the native one is not built or cannot start; "python" never starts the native one; `player.native` says which plays) and its audio-thread worker drives the engine's feeder (`NativeFeeder` or `PCMFeeder`). Each engine has its own buffer setting (`native_buffer_ms`, default 20; `python_buffer_ms`, default 80): the dialog shows the playing engine's with the rest and the other's under Advanced (`set_audio_engine`). The output device (`output_device`, by the name the playing engine lists: `player.output_devices()`; "" the system's default) changes while playing (a device is found by its name, or the only one of that name but its Windows instance number, "Speakers (2- DDJ-400)" plugged in again as "(3- DDJ-400)": `device::pick`; one not there: the master plays on the system's default, and stays there (intended: a master that plays is left as it is) until the device is picked again or the engine restarted (Restart Audio Engine), a bus on a device of its own (headphones, booth) waits for its device, tried each second, never taking another: `device::NOT_PRESENT`, so a CUE never reaches the speakers and an exclusive stream never locks the master out; a failure said once until it changes, an audio client's code in words: `device::explain`), at the session's format (converted by the system); on the native engine the master goes to a channel pair of it, the headphones and the booth to channel pairs of it or to devices of their own (`set_routing`: `audioengine/native/AGENTS.md`). A scrub's positions reach the engine at most every `SCRUB_INTERVAL_MS` (30 ms, the newest; the views follow the drag itself); the decoded PCM goes to the native engine in a shared block (`client.share_pcm`, `NativeFeeder.adopt` in the decode thread), which is also `DataModel.predecoded_pcm` (no copy).

## The settings files
- Keep root-level `config.json` available, and `deck.json` beside it (both the user's, gitignored). `config.json` holds the settings that seldom change (the settings dialog's); `deck.json` what playing changes (`config.deckconfig`: the time stretch's MT, the metronome, the TRIM, the tempo range, the MIDI input on / off, the toolbar's switches and levels, the effects picked, Search by Music's microphone; the deck's momentary state, FX ON, the EQ / COLOR knobs, CUE, is not kept), written a second after it changes (`SettingsStore.deck_changed`; `SettingsStore.save` both), the MT button and the metronome's on / off too (`AppWindow._on_timestretch_toggle` / `_on_metronome_toggle`: each applied alone; a whole settings save there filled the settings window and pushed the click's sound again, the waveform jerking). Where `deck.json` is missing, its values are taken from `config.json`'s playbackconfig once. The settings have one owner, `core.settings.store.SettingsStore` (made by the start, `app.startup`, handed to `AppWindow`, installed for `store.current()`): `load_cfg()` reads both once, at the start (`app.main`), and the store keeps them in memory and alone writes them (`save`: the settings dialog's, both files, then `changed` (old, new); `deck_changed`: deckconfig changed in place, deck.json a second later, at once when the app quits); every other part reads `current()` (no file read), a spawned worker process is given the settings it runs with (`tests/test_settings_boundary.py`: `load_cfg` / `save_cfg` / `save_deck` named nowhere else). `load_cfg()` rewrites a file only where it is not what it reads as (missing, a key added or migrated; Windows refuses to replace a file another process holds: `system/atomic_io` tries a replace again for half a second); one it cannot read (not JSON, not UTF-8, not an object) is moved aside as `<name>.unreadable-<time>` before its defaults are written, and the start says so (`config.unreadable_settings()`). Every editable value has one place it is edited: the settings dialog shows none of the main screen's (the MT button, the TRIM knob, the metronome's on / off, the toolbar's). A library restored from a backup brings its settings (`config.restored_settings`: the package's, but what describes this device stays this device's: the audio, the microphone, External Sync, every file path setting), saved through the store before the app starts again (`core/library/AGENTS.md`, Backup and moving).

## Analysis Flow
- A load onto the deck (a drop on the deck, the library's load: `sig_request_load_track`, External Sync) goes to `AppWindow.load_track`: the file plays at once (decoded; a new file shows its tags meanwhile and the decoded length) and `AnalysisWorkflow.analyze(path, listener=)` gives the deck its stored analysis (a library track's at once, a new file's when analyzed: the analysis's results alone are applied then, `DataModel.load(keep_audio=True)`, the playback goes on; applied only while the deck still holds that file). A file only analyzed into the library (dropped on the library, a playlist's new files, Reanalyze on files not analyzed yet) goes by `sig_request_analyze` (no listener; a library track's is not analyzed again).
- Full-track analysis runs in a spawned subprocess via `core.workers.analysis.AnalysisWorker`, at most `analysisconfig.max_parallel_analyses` at once (Settings > Analysis > Global, default 4; the setting as it is when one starts; raised, the waiting ones start at once: `AnalysisWorkflow.settings_changed`): the others wait their turn in `AnalysisWorkflow._waiting`, in their order, the deck's track (a request with a listener, or a waiting file loaded onto the deck) ahead of the files only going into the library; a slot freed starts the next, a cancel drops the waiting. The editor's partial reanalyses (`SegmentReanalysisWorkflow`) are not counted: they start at once. The process runs with one BLAS thread (`threadpool_limits` in `core/workers/analysis.py`): the analysis runs its own threads, and BLAS threads on top only competed (the outputs are the same; a track about 20 % faster, a third less CPU).
- The worker calls `analyze_for_library` (`core/workers/analysis.py`): the file's tags read (`core/tags/reader.py`), `analyzer.pipeline.track.analyze_track` run, its `TrackAnalysis` made into what the library stores.
- The pipeline (`analyzer/pipeline/track.py`):
  - decode/load audio,
  - HPSS split (always on, not a setting; its median filters are a sliding median kept sorted, `analyzer/audio/running_median.py`, equal to scipy's `median_filter` and several times faster),
  - overview waveform (its own 48 kHz decode: min / max of 32768 columns, the power of 12 log-spaced bands in 8192 columns, and the detail waveform's three-band scale),
  - beat tracking (`analyzer.beat.general.track` on the frame features; frames on the fixed grid `frame_features.FRAME_HOP_LENGTH` (256); the models were trained on 22050 Hz HPSS frames; every analysis runs at 22050 Hz (`analyzer.settings.ANALYSIS_SAMPLE_RATE`, not a setting) with HPSS, so the tracker reads the analysis's own frames): per training seed, tempo candidates from the activation's periodicity -> section decoding into steady (tempo, phase) grids with one section cost -> exact tempo / phase fit -> sudden vs gradual tempo changes (linear ramps, continuous or with a jump at one end) -> bar-supported half-beat phase (bars of 2, 3 or 4 beats) -> metronome critic (3:2 / 4:3 misreads) -> tempo-change boundaries on the refine onset -> slow tail held -> drifting sections -> tiny re-syncs merged -> junction rules (no too-close / too-far beats at grid changes) -> bars (a Viterbi over 3- and 4-beat bars on two downbeat observers; an odd bar costs, a new section starts free); then the seed whose grid agrees most with the other two. Every tempo is read in the octave from BPM min. The rows have `inizio` on a downbeat and `ts` the bar length (`bars.to_rows` splits a row where the bar length changes), so the segments always rebuild the beats and downbeats,
  - JumpCUE detection,
  - key analysis (`analyzer.key.chord_key.analyze_keys` on the beats, the downbeats and the phrase starts; no keys when it fails),
  - Search by Music's index (`analyzer.search.music.index.index_audio` on the decoded stereo, the HPSS's harmonic part and mask and the frame features' melody contours already made, about 2.2 s of CPU a 4-minute track; Index Now, decoding and making its own HPSS mask, about 3 s; `searchconfig.music_index`, on by default; written to `music_search.db` once the track has its uid; a failure leaves the track unindexed, never the analysis undone),
  - the results handed back (the process never opens the library: its result carries ``store``, the segment rows, the music entry, the Variants' fingerprints and the cover's bytes) and stored by the library's owner (`core.library.jobs.store_analysis`, a write job: `AnalysisWorkflow._on_success`): the track's row (a track already in the library keeps the user's metadata, the row read then: a reanalysis, and the analysis of a track whose stored one did not read; a new track given its uid), tag sources, segment tables, NPZ (`FeatureNPZStore`), thumbnail, Search by Music's entry,
  - the Variants' fingerprints (made by the pipeline after the index, `analyzer.search.variants.track_fingerprints` on the beats and the overview's bands, always; stored by the owner, `core.library.variants.put`, then queried against the library's; a failure leaves the track out of the Variants, never the analysis undone), the Mix Candidates' beats' features (the pipeline's frame features pooled into the beats, `analyzer.search.mixability.beat_features`, always; stored with the bars made of them, `core.library.mixability.put`; a failure leaves the track out of the candidates until Index Now), then, for a new track only (not in the library before this analysis), its versions' tie-ups (`core.library.tieups.match_new_track`), in the same job; the GUI looks a new track left without on the web when Settings > Library says so (`core.workflows.tieup_web`).
- A library track's stored analysis is read by the library's owner (`AnalysisWorkflow._start`), no process started.
- Reanalyze-track requests (`sig_reanalyze_requested`: the path and analysis settings for this run only, or None) force a fresh full analysis and overwrite stored results.

## Segment Reanalysis
- Partial reanalysis is orchestrated by `core.workflows.segment_reanalysis.SegmentReanalysisWorkflow`.
- Work is offloaded to a subprocess via `SegmentReanalysisWorker`: the editor asks with a `ReanalysisRequest` (`EventBus.sig_segment_reanalyze_requested`: what is read again, `kind`, and the track's current marks it reads), the process answers with a `ReanalysisResult` (`core/workers/segment_reanalysis.py`).
- Supported modes currently include:
  - beat segment reanalysis,
  - static key selection reanalysis (`chord_key`: the key with the most evidence over the selection),
  - dynamic full key reanalysis (`chord_key` on the editor's current beatgrid, bars and phrases),
  - JumpCUE reanalysis (with AutoCUE on JumpCUEs, the AutoCUE JumpCUE goes where the editor's current phrases' lead-in ends; with AutoCUE on CUE points, the Phrase page's CUE button places it),
  - phrase reanalysis (the whole track on the current beatgrid; the CUE points stay).
- Results go to the loaded track as edits, with or without the editor shown (`DataModel.set_beatgrid` / `set_key_segments` / `set_phrases(normalize=True)` / `set_jump_cues`, and `set_automatic` for a whole-track reanalysis's automatic result): undoable, saved with the editor's next save; they are not a separate analysis system.

## The loaded track
- `DataModel` (`core.track.model`) holds the live in-memory track state, its one owner: `analysis` (the `StoredAnalysis` as loaded) and `properties` (read-only), `duration_sec`, `album_art`, the predecoded audio, and the marks as edited (`beats`, `tempo_segments`, `key_segments`, `phrases`, `jump_cues`, `cue_points`) with their undo history; changed through its methods alone (above).

## External Sync
- `core.playback.external_sync.ExternalSyncController` follows another program's deck: the track it has loaded and its position, received as OSC over UDP (`OscReceiver`, its own thread keeping each deck's newest state; the GUI takes it at the view's frame rate), one message per deck: `/mixlyzer/deck/time  i deck s path T|F loaded T|F active d|f seconds` or `/mixlyzer/deck/samples  i deck s path T|F loaded T|F active h|i samples i rate` (rate 0: the file's own; a flag may be an i 0 / 1). The deck followed is the lowest-numbered loaded and active one; a deck silent for `STALE_SEC` is gone. Settings > External Sync: on / off, the address and port (127.0.0.1:39321 by default), the status, the message format.
- It listens on this computer only unless the settings name another address; then only library tracks are followed (no analysis started from the network). A path must be a local file: UNC / `//host` spellings refused before and after a link is resolved (opening one sends the user's credentials). Packets are parsed strictly (`core.playback.osc`: lengths checked, only i h f d s T F, 8 KB at most) and refused whole when malformed.
- Mixlyzer reads no other program's memory. The memory reader that used to be here is its own program, the External Sync bridge (github.com/hygn/Mixlyzer_extsync): it reads a DJ program's deck state through the user's pointer chains and sends these messages. The user's chains live in that bridge's git-ignored `bridge.json` and are never committed to either repository (local pre-commit / pre-push hooks refuse them).
- When enabled, local playback/load controls are intentionally restricted.
- If you touch External Sync config or behavior, keep `core/settings/config.py`, `ui/config/`, and `app/window.py` aligned.
