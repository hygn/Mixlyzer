# AGENTS: core/library/ (Mixlyzer)

The details of the library and the analysis library (`core/library/`, `core/analysis_library/`): their one owner, the jobs, what is stored where. The root `AGENTS.md`'s rules (run, layers, owners, change guidelines) apply here too; read it first.

## Map
- `library/`: the library (library.db, the thumbnails, music_search.db, variants.db, mixability.db; the tracks' stored analyses are `analysis_library/`'s, below, kept by the same owner), its one owner and every operation on it, behind one boundary (`core/library/__init__.py` maps it; `tests/test_library_boundary.py` holds it: outside `core/library/` and `core/analysis_library/` no `sqlite3` but `core/tieups/web.py`'s own web cache, no import of the modules inside but a type under `TYPE_CHECKING`, no path of a track's `{uid}.npz`, `analysis_path`). Outside code uses three modules:
  - `service.py`: `LibraryService`, the owner (made by the startup, `app.startup`, handed to `AppWindow`): a thread of its own with the one connection to library.db and the others' files; the jobs run there in the order asked (a read asked after a write sees it). The GUI asks `read(job, *args, done=, failed=)` / `write(...)` (``done`` on the GUI thread, a deleted widget's callback skipped; after writes the snapshot is read again before their ``done``); another thread of the app asks and waits, `call(job, *args, write=)` (the tie-up web lookup, the Export tab's tag writer, the Rekordbox XML sync, Search by Music's index loading; refused on the GUI thread, which would freeze, and from a job, which would wait for itself). `LibrarySnapshot` (the tracks, their readings and tie-ups, the 초성 search's keys and the names' sort keys stored with them (`initials`, `sort_keys` in the search settings' `name_sort`: `track_name_keys`), the playlists and their entries, the Variants' relations; ~35 ms at 400 tracks) is sent with `updated` and `EventBus.sig_lib_updated`: the GUI reads it at once (`find_file`, `track`, `playlist_tracks`; External Sync's questions).
  - `jobs.py`: every operation on the library, one function each, `job(lib, *args)` with `Library` (`db`, `path`, `features`), grouped by what they serve (tracks, readings, playlists, the structured searches, tie-ups, the indexes, thumbnails, an analysis stored, tracks removed: the last two write the stored analyses too). A new operation is a new job here; its callers name it (`library.write(jobs.save_tieup, uid, t, old, versions, done=...)`), never SQL.
  - `records.py`: what jobs take and give (`TrackRow`, `PlaylistRow`, `IndexTrack`, the segment rows, `field_readings`; the ids' one spelling is `system/ids.py`'s `canonical_uuid4`).
  - `package.py`: the library package (`.mxlib`), below (Backup and moving): its export is a job (`jobs.export_package`); reading, checking and unpacking one is this module's, used by the restore's thread (`core.workflows.library_backup`): a folder being unpacked is no library yet, its files the unpacker's until the app is started on it.
  - Inside, used by the jobs alone: `db.py` (`LibraryDB`: the tracks, readings, tag sources, playlists, segment tables, the transition search), `tieups.py` (the tie-up tables and their SQL; the domain is `core/tieups/domain.py`), `thumbnails.py`, `music_index.py` (music_search.db; `LandmarkIndex`, the read-only connection the owner lends Search by Music's searches: on its thread they would hold the other jobs), `variants.py` (variants.db), `mixability.py` (mixability.db).
  - Worker processes compute only and never open the library: they are given what they read and hand back what the owner stores (the analysis: `arrays` and `store` in its last item, `jobs.store_analysis`; Re-read Library: `jobs.reading_texts` in, `jobs.apply_readings` / `apply_work_readings` out; Index Now: `jobs.index_plan` in, `jobs.store_music_entry` / `fingerprint` out; Reoptimize: `analysis_jobs.training_tracks` and their annotations, `training_annotations`, 50 tracks a job so the GUI's jobs run between, in; `optimizer.library_tracks` holding them in the process).
- `analysis_library/`: the analysis library, each library track's stored analysis `{libpath}/{uid}.npz` (`core/analysis_library/__init__.py` maps it), kept by the library's owner (one thread for all the library's files: an analysis stored or a track removed writes library.db and the NPZ in one job). `jobs.py` (imported as `analysis_jobs`): every operation on the stored analyses alone, `job(lib, *args)` as the library's (`analysis`, `fingerprint_source` (the beats, length and overview only), `mix_source` (those and the tempo rows), `features_stamp`, Reoptimize's `training_tracks` / `training_annotations`); the jobs that write library.db too are `core.library.jobs`' (`store_analysis`, the editor's `save_edits` of a `TrackEdits`, `remove_tracks`), and this package imports nothing of `core.library` (below it); `stored.py` what a stored analysis holds, the one place that knows its keys and blocks: `StoredAnalysis` (`from_arrays`: the arrays as the app reads them, every mark typed, the overview an `analyzer.audio.wave_overview.WaveOverview`), `arrays_of` (an analysis's results as stored), `TrackEdits` / `apply_edits` (the editor's save, each mark's block replaced whole), `annotation_of` (Reoptimize's `analyzer.training.library_tracks.Annotation`); outside, code reads the fields, never a stored key, and uses the jobs, `stored.py` and two conversions only (`cue_points.as_stored`, `jump_cues.jump_cue_groups_of_pairs`: `tests/test_library_boundary.py`); `cue_points.py`, `jump_cues.py`, `phrases.py` each mark's stored block; inside, used by the jobs and the owner alone: `store.py` (`FeatureNPZStore`, the file format: flattened keys, NumPy values only, written atomically; `load_keys` decompresses only the keys asked for).

## Data & Persistence
- Track metadata lives in `library/library.db` in the `tracks` table, keyed by `uid` (PRIMARY KEY, canonical UUIDv4).
- `track_readings` (uid, field, slot) holds the romanized readings of each track's title / artist / album (`core.search.reading`): the search's intermediate representation, up to 7 a field, each with its source (ja, zh, yue, ko-hanja, vi, zh-tw, ko, text, or user). The readings the user added (the track panel's Search Index tab: only the cells typed there; source `user`) are kept and come first; the automatic ones after them are made anew in the stored languages whenever the track is written (`LibraryDB.upsert` -> `refresh_readings`, `core.library.db.field_readings`), so a language unchecked removes only automatic readings. An automatic reading the user removed (emptied, Delete, or typed over in the grid) is kept in `track_reading_removals` (uid, field, reading) and left out from then on, whatever the languages; typed again, it is the user's. Settings > Search's Re-read Library (also started when what the stored readings depend on changes: `searchconfig.stored_readings()`) reads every track again: the library's owner gives a spawned process every text (titles, artists, albums, the tie-up works' names), the process reads them (`core/workers/reading_refresh.py`: the readers are Python, the GUI's interpreter lock spared) and the owner writes the readings back, 50 tracks a job (`core/workflows/reading_refresh.py`). The library's text search matches Title / Artist / Album by these too.
- `track_name_keys` (uid, field) holds what the search and the sort make of a title / artist / album's text and readings (`core.search.reading.name_keys`): its 초성 keys (one a line) and its sort keys in each order of Settings > Search's Sort Names (`abc`, `hangul`, `gojuon`), with the `rules` that made them (`reading.NAME_KEYS_RULES`). Written with the field's readings (`LibraryDB._write_readings`: an upsert, Re-read Library, the user's readings); the fields missing them or made by other rules are given them again when the owner opens the library (`refresh_name_keys`: a library of an earlier version, the rules changed). The snapshot reads them (`LibrarySnapshot.initials`, `sort_keys`); none are computed on the GUI thread. The tie-up works' names have theirs in `tieup_name_keys` (`core.library.tieups.refresh_name_keys`: made when a name is added, again with Re-read Library and other rules). Settings > Search's Rebuild Sort Index makes every one again (`jobs.rebuild_name_keys`).
- Playlists (`playlists`, keyed by their own UUIDv4 `uid`) hold one `playlist_tracks` row per entry, (`playlist_uid`, `position`) -> `track_uid`: a track may be in a playlist more than once, so the UI addresses an entry by its position (reorder / remove), never by the track. Removing a track removes its entries and closes the playlists up. Playlists are in folders, a tree: `playlist_folders` (uid, name, `parent_uid`: NULL at the top) and `playlist_folder_items` (playlist -> its folder; none: at the top), both made beside the earlier tables (no migration); a folder's children, its folders and playlists, are in one order, each one's `sort_index` (a playlist's `playlists.sort_index`) numbered within its folder (`LibraryDB._children`; `records.playlist_children` the snapshot's view). Moved within a folder or into another (`move_playlist_node` / `_by`, a folder never into itself or a folder inside it); a folder deleted with every folder and playlist in it (the tracks stay). A playlist's name is one in its folder, letter case aside (`LibraryDB._check_playlist_name`, on making, renaming and moving one into another folder: the same name in another folder is another playlist, as rekordbox's); the table holds no UNIQUE (a library.db made before keeps its whole-library one until the table is made again); a folder's name is not unique.
- BPM and key transitions are also persisted in:
  - `track_bpm_segments`
  - `track_key_segments`
- library.db's rows made from a track's marks (`tracks.bpm` / `key`, `track_bpm_segments`, `track_key_segments`, `track_phrase_sections`) are made by one function, `core.library.segments.track_index` (the BPM `dominant_tempo`, the key `key_rows.main_key`), for every writer, each in one transaction with the NPZ saved last (`LibraryDB.write_track_index`; `LibraryDB.tx` nests as savepoints, only the outermost commits): the full analysis (`core/workers/analysis.py` makes it, `jobs.store_analysis` writes it), the editor's save (`jobs.save_edits`, when Settings > Library's "Update the library database when the editor saves" is on, `libconfig.sync_stored_analysis`, default on; off, the NPZ alone) and the library's sync (Settings > Library > Library Database's Sync Now: `core.workflows.library_sync`, `jobs.sync_index`, asked first, No by default: it replaces the BPM and key typed in the Edit Track tab too, as intended; 50 tracks a job, every track's rows written from its stored marks, `analysis_jobs.stored_marks`, only where they differ (`LibraryDB.update_track_index`), the snapshot read once at the end where a row changed (`jobs.index_synced`); the tracks changed and those without a stored analysis that reads (a damaged file too) counted; the rest of the user's metadata and the NPZ never written). The NPZ is the truth, library.db's rows what is made of it.
- Tempo segments are rows `[start, end, bpm, inizio, ts_num, bpm_end]` (`analyzer.music.tempo_rows`). A `bpm_end` that differs from `bpm` is a linear tempo ramp (tempo linear in time from `start` to `end`; its beats come from the closed-form phase); rows without it (5 columns, older data) or with it equal are steady. `inizio` is a downbeat on the row's own grid. `track_bpm_segments.bpm_end` mirrors it (NULL = steady): transition search reads a ramp as a change from its start to its end tempo, and a phrase section inside a ramp gets the tempo at its midpoint. The editor keeps ramp rows (cut / merge / shift follow the tempo line; Assign makes the row steady at the reference BPM; the ramp start / end buttons make the reference BPM the row's start or end tempo, its first beat kept), and the Rekordbox export (which has no ramps) writes a ramp as steps of steady tempo, one TEMPO entry each: a step per beat, or several beats while every beat stays within Settings > Library's Tempo ramp tolerance (`libconfig.rekordbox_ramp_tolerance_ms`, default 1 ms), measured as written (Inizio in ms, the BPM rounded down to 0.01 so a step never puts a beat just before the next one's).
- Numeric feature arrays live in `{libpath}/{uid}.npz` (the analysis library: `core.analysis_library`, its `store.FeatureNPZStore`, read and written through `analysis_jobs` alone). Only what is read is stored: beats, tempo/key segments, the overview waveform (`wave_minmax_np` / `wave_minmax_ref`, `wave_bands_np` / `wave_bands_ref`, `wave_detail_band_ref`), duration, sr, tempo_global, and the JumpCUE / CUE point / phrase blocks. The keys and blocks are known to `core.analysis_library.stored` alone (and `store.py`, the file format); the app reads a `StoredAnalysis`. The editor's save replaces each mark's block as a whole (`core.library.jobs.save_edits`, `stored.apply_edits`).
- Track identity across DB, NPZ, thumbnails and playlists is the `uid`; the file path is an editable attribute (`LibraryDB.set_path`; the track panel's Edit tab). `tracks.path` stays UNIQUE (one file, one track).
- `tracks.path` is stored as given, never normalized (case / separators can name different files on other file systems). A path that may spell a library file differently (a drop, External Sync's deck path) is looked up by the file it opens (`LibraryDB.find_file`) and then used as stored.
- A library track whose file is missing is not loaded: the app says so and asks the user for the file's new location (no guessing by name or content).
- `track_tag_sources` (uid, field, slot) holds where the track's file holds its title / artist / album / comment (`core.tags.writer` spellings, as `vorbis:PERFORMER` or `mp4:titl`; one row with source "" when none does: a title from the file name, a field read empty): recorded by the analysis when it reads the tags (`core.tags.reader.read_tag_sources`: the spellings holding the values read). The analysis reads the tags and the cover with the app's own readers, no native tag library (an outside file): `tag_writer.read_fields` / `read_picture` for FLAC / MP3 / AAC / WAV / AIFF / MP4 (MediaInfo's order of places, `LEVELS`; the cover the front one, else the first), FFmpeg for the other formats (`decoder.read_metadata` / `read_cover`); the cover is decoded by Qt in the format its first bytes name (JPEG, PNG, GIF, BMP, WebP), at most `COVER_MAX_BYTES`, used by the Export tab's File Tags to write each value back there. BPM and key are not read from the tags (the analysis gives them), so they have no source: they are written to the format's own places. A track without sources (added before they were kept, or given another file: `set_path` clears them) gets them found from its file on its first write.
- Search by Music's index lives apart from library.db in `{libpath}/music_search.db` (`core.library.music_index`): made from the audio alone (all of it dropped and rebuilt when `music_index.METHOD` changes), large (the landmarks, about 130 KB a song), never the user's own. Tables `meta` (the method), `melody` (uid, the file's size / time, the reference lines per frame size), `landmark_song` / `landmark` (hash, song, t; WITHOUT ROWID, clustered by hash). Written by the analysis and by Index Now (Settings > Search > Search by Music: `core.workflows.music_index`: the library tracks not indexed yet, their audio read by up to 4 spawned processes at a lower priority, each entry handed back and stored by the library's owner, the tracks gone from the library dropped; a non-modal progress window as the Rekordbox XML sync's); the search window reads it (a read-only connection the owner lends it) and holds the reference lines in memory.
- Tie-ups (`core.tieups.domain`) live in library.db (the user's own data, made by `LibraryDB.connect` through `core.library.tieups.create_schema`): `tieup_work` (id, category), `tieup_name` (work, name, lang `ll-RR` (a CHECK), type: official / synonym / short / search_hint, is_primary, rank, its readings), `tieup_url` (work, url, label, rank), `tieup` (track_uid, work, role, seq, detail, rank; the key track, work, role, seq; gone with the track). The Tie-ups tab and the Tie-up Works window write them at once (no Apply).
- The Variants' index lives in `{libpath}/variants.db` (`core.library.variants`), as Search by Music's: made from the analysis's features (beats, `wave_bands_np` / `_ref`), never the user's own. Every fingerprint carries its method (`analyzer.search.variants.METHOD`: the algorithm and the versions of the features it reads, `analyzer/beat/grid_version.py`'s `BEAT_GRID_VERSION` and `analyzer/audio/wave_overview.py`'s `WAVE_BANDS_VERSION`: raise them when the tracker's beats or the stored bands change), so a method's change keeps the index: fingerprints are compared only within one method, a track analyzed or indexed gets the current one (Index Now takes the tracks without it), the relations an earlier method found stay meanwhile, and once a track has the current method its earlier fingerprints go (`prune_old_methods`, at Index Now's end); an index made before methods were kept is dropped and made again. Tables `variant_method` (id, name), `variant_song` (id, uid, method, the codes: 5 bytes a frame; one per track and method), `variant_hash` (method, hash, song, frame; WITHOUT ROWID), `variant_pair` (a < b, the method, the relation, b's to a: same / a_instrumental / b_instrumental / vocal, each side's cover, the mix's agreement; `pairs()` the current method's first). A track is stored, then queried against all stored of its method (one writer, the library's owner: of two tracks, the one stored second finds the other); a track stored again (reanalysed) loses its fingerprints and that method's relations first. Written by the library's owner: an analysis's results stored, and Index Now (from each track's NPZ, without its audio). Beatgrid edits do not refresh it (a reanalysis does). A track removed from the library leaves it and Search by Music's index in the same job (`jobs.remove_tracks` -> `jobs.drop_from_indexes`: each a pass over its index); Index Now drops what is left, and so does the start: `jobs.check_stores`, the first job of the library's owner (`app.startup`), makes every store beside library.db agree with its tracks (library.db's rows keyed by a track (the tie-ups' too, the playlists closed up), Search by Music's index, the Variants', the thumbnails dropped; a stored analysis of no track moved to `{libpath}/orphaned_analyses/`, never deleted: it may hold the user's edits), said on the console; a library.db without tracks beside stores that have some is taken for a library.db lost and nothing is touched. The snapshot's Variants relations are the library tracks' only.
- The Mix Candidates' index lives in `{libpath}/mixability.db` (`core.library.mixability`), as the Variants': made from the audio and the analysis, never the user's own. One row a track (`mix_track`): its beats' features (`analyzer.search.mixability.BeatFeatures`, float16) with the beat times they were read on and their method (`mixability.FEATURES`), and the bars made of them with the stored downbeats and overview (`Bars`, float16 rows) and theirs (`analyzer.search.mixability.METHOD`). Written by the library's owner: an analysis's results stored (the analysis's features), Index Now (the tracks whose stored beats are not those of their features: their audio read in its processes on the beats the plan gives them, `jobs.store_mix_features`, refused when the beats changed meanwhile; at its end the bars of an earlier method made again from the features, `jobs.stale_mix_bars_again`), and the editor's save (`jobs.mix_bars_again`: the bars follow the downbeats as edited while the beats are the features'; other beats wait for Index Now). Dropped with a track as the other indexes, checked at the start (`jobs.check_stores`), packed in a backup (`package.MIX_DB`). Read by `jobs.mix_candidates` (every track's bars, the phrases, tempo and key rows from library.db: `LibraryDB.mix_marks`; the loaded track's versions left out), ranked by `core.search.mixability`.
- Album art thumbnails (downsampled, JPEG) live in `{libpath}/thumbs/{uid}.jpg` (`core.library.thumbnails`): written by the full analysis, removed with the track; the library table shows the top of each as its first column.
- A JumpCUE group's colour is a preset index (`graph_color_idx`, presets in `core/marks/colors.py`), independent of its group number (`graph_id`); no RGB is stored. In memory it is the group's `JumpCueGroup.color_idx` (read and written whole by `core.analysis_library.jump_cues` `extract_jump_cue_groups` / `build_jump_cue_block`; the detector's pairs become a block by `build_jump_cues_np`, the analysis's path alone).
- Keys are kept in two states in the NPZ like the JumpCUEs: `key_segments` (the user's, replaced by edits) and `key_segments_auto` (the automatic result, replaced by the full analysis and the editor's whole-track key reanalysis, saved with the editor's next save). The key optimizer learns from the tracks where they differ; do not write edits into `key_segments_auto`.
- CUE points (`cue_points_np`, with a colour preset `cue_color_idx`) are the user's: the full analysis makes them from the phrases by the per-label rules in `config.cuepointconfig` (Settings > Analysis > CUE; LEAD_IN has no rule), after that only the CUE page edits them (phrase edits do not regenerate them), or the Phrase page's CUE button replaces them with what the same rules give the current phrases.
- Phrases cover the track when read: stretches without a stored phrase (all of a track analyzed without phrases) are `UNASSIGNED` (`core.marks.phrases.fill_unassigned`). It is shown and edited like a label but never stored (`assigned_phrases` on save), so it never reaches training data.
- Phrase labels are the fixed `core.marks.phrases.PHRASE_LABELS` (no custom labels). How each is shown is a setting (Settings > View > Phrase labels: an alias and an overview abbreviation, empty = the label / its first letter), applied through `core.marks.phrases.set_phrase_label_names`; stored data always keeps the label itself.
- JumpCUE letters are slots (rekordbox hot cue letters A-Z): the analysis letters them by point; edits keep each cue in the slot the user gave it (no relettering by time). A JumpCUE's user name is its `cue_comment` (equal to its letter = no name). CUE points are rekordbox memory cues: always in time order, no letters; a CUE point's name is its `cue_label`. The Rekordbox XML writes them as memory cues (`POSITION_MARK` `Num="-1"`, with their colours) and the JumpCUEs as hot cues.
- The Rekordbox XML's PLAYLISTS are the library's playlists as they are nested (`RekordboxXmlDocument.set_playlists`, from `jobs.playlist_tree`): under rekordbox's ROOT, a folder `NODE Type="0"` (its `Count`), a playlist `NODE Type="1" KeyType="1"` whose `TRACK Key`s are its entries' `Location`s as COLLECTION writes them (rekordbox finds a track by its file; an entry whose track COLLECTION lacks is left out), replaced whole at every write of the XML (every sync mode), and on their own a second after the playlists last changed (`core.workflows.rekordbox_sync`: the snapshot's playlists, folders or entries read again, told by identity; mode `playlists`, an XML not made yet made whole).

## Backup and moving
- The library package (`core.library.package`, `.mxlib`) is a backup and a move to another device alike: unpacked on the same device it is a restore, on another a move. Only when the user asks (Settings > Library > Backup: Back Up Library… / Restore Library…, the file picked each time); no automatic backups, no generations; syncing two devices both ways is not done (an imported library goes its own way).
- A zip, stored (the NPZ and JPEG files are compressed already), ZIP64; its names only the fixed ones and patterns of `package.allowed` (`library/library.db`, `VERSION`, `music_search.db`, `variants.db`, `mixability.db`, `library/<uid>.npz`, `library/orphaned_analyses/<uid>.npz`, `library/thumbs/<uid>.jpg`, `settings/config.json` / `deck.json`, `user/shortcuts.json` / `midi.json`, `user/models/<an analysisconfig *_parameter_path setting>`, `cache/tieup_web.db`, `featurecache/<a *_feature_cache_path setting>/...`), and `manifest.json` (the format and its version, the library version, when and on which OS it was made, the track count, every track's path and file size, each file's size and SHA-256). Everything rebuildable is packed too (the indexes, thumbnails, the tie-up cache), so a restored library opens without rebuilding; the feature caches only when asked (`libconfig.backup_feature_cache`, off by default). No audio file.
- Export: one job of the library's owner (`jobs.export_package`, asked as a read: no other job runs meanwhile, so library.db and the NPZ files are of one moment): the databases copied through SQLite's backup API (the tie-up cache by `core.tieups.web.copy_cache`), the settings as the store holds them, the user's files where they are (`core.workflows.library_backup.user_files`); written to `<file>.partial`, renamed at its end; progress and cancel (no file left).
- While a backup or a restore runs its window is application modal and the controller's GUI actions are dropped (`AppWindow._hold_library`): nothing edits the library, the settings or the loaded track meanwhile (the deck plays on); a window running ignores Esc and its close.
- Restore (`core.workflows.library_backup.LibraryBackup.restore`, a thread; `ui/windows/library_backup.py`'s window): the package read and checked (`read_package`: a zip of this format, the library version this app's, else refused: no migrations during development; every name allowed, each member stored and of the manifest's size); a new library folder (new or empty; by default `<library>-restored-<time>` beside the one in use, which is never touched); the stored paths' roots (`path_roots`: by drive and first folder, Windows paths read as Windows', in any letter case) each joined by the user to a folder on this device (`check_mapping` counts found / another size / missing by the stored file size: it only confirms the user's mapping, nothing is looked for by name or content; a root that exists here as it is is filled in, its paths kept as stored); unpacked beside the folder and renamed at the end, each file's SHA-256 checked, each database's integrity checked and refused when it holds a trigger or view (the app makes none; one in another's package would run as the app writes; an earlier version's leftover table is only data), the paths under a mapped root rewritten (`remap_path`; one another track already has left, counted). The user's files are unpacked first beside their places (`<name>.restoring-<time>`, each hash checked) and put in place once the library is (an existing one kept beside as `<name>.before-restore-<time>`; a failure before leaves the files in use as they were); then the tie-up cache's rows (`core.tieups.web.restore_cache`: its table only), the feature caches into their folders; the window saves the settings (`core.settings.config.restored_settings`: the package's, but this device's audio (playbackconfig), microphone, External Sync and every file path setting; the library the new folder; the music folders and the Rekordbox XML joined by the same mapping, else as written where they exist, else this device's) and starts the app again (`app.window.restart_app`), which opens the new library through the start's checks. Edits the editor has not saved stop a restore first.
- `tests/test_library_package.py`: a library packed and unpacked whole, its music moved and joined, the same folder kept, a cancel, and every package refused that this app does not make (not a zip, another version or a newer format, a name out of the folder listed or not, bytes changed, a compressed member, a database with a trigger, a folder not empty); the settings restored keep this device's audio and paths.
