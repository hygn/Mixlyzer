# AGENTS (Mixlyzer)

Working notes for AI/automation agents editing the Mixlyzer codebase.

## Run & Environment
- Python 3.12+.
- Dependency management uses `uv`.
- Install deps with `uv sync` (with the development group: Babel, for `build/translations.py`).
- Launch the app with `uv run python -m app.main`.
- The native audio engine (`audioengine/native`) is built with `uv sync --group native` then `uv run python build/audio_engine.py` (git, Rust, and a C compiler: on Windows llvm-mingw + the `stable-x86_64-pc-windows-gnullvm` toolchain; the script's docstring has the details); its output, `audioengine/native/bin/`, is not committed. Without it the app plays on the Python engine. A running app holds `bin/`'s executable: close it before rebuilding.
- Keep root-level `config.json` available. `load_cfg()` reads and rewrites it; one it cannot read (not JSON, not UTF-8, not an object) is moved aside as `config.json.unreadable-<time>` before the defaults are written, and the start says so (`config.unreadable_config()`).
- Keep a root-level `ffmpeg.exe` (Windows) / executable `ffmpeg` (Linux, macOS), or provide FFmpeg on `PATH` for `core/audio/decoder.py`.
- Do not run the app as administrator (Windows) or root (Linux, macOS); `app/main.py` explicitly blocks it.
- Windows, Linux and macOS are supported (`core.os_support`); on any other system the app warns at the start and runs on the fallbacks.

## Repo Map
- `app/`: Qt entrypoint and top-level window wiring.
  - `main.py`: app bootstrap (the UI language first, before the UI is imported), dark palette, font loading, library-version migration flow. Kept light: a spawned worker process imports the main module again, so `app.window` is imported by the startup, not at the top.
  - `startup.py`: the startup splash (the task, what it is doing, a Task and an Overall progress bar, and under them the console's last lines: `startup_console.py`, `ConsoleLines` tapping sys.stdout / stderr from `main()`'s start (the print hook, installed later, writes through it; taken out when the splash closes), drawn as a terminal's: the time since the start, a coloured tag per source (`[Startup]`, `[AudioEngine]`, ...), a finished task's time right-aligned, a failure in the danger colour; the engine's lines, printed on its relay thread, drawn at the next repaint) and the slow work done before the window opens, in order: the heavy imports, the Python audio engine's numba kernels (JIT, from numba's disk cache; skipped when the native engine is built), FFmpeg's first run, the search readers (`reading.warm_up`), every stored reading's search keys (`reading.keys`' LRU cache), then `AppWindow(progress=)`. numpy's and scipy's OpenBLAS load with one thread in this process (`one_blas_thread()`, first in `main()`: the GUI does no heavy linear algebra, and each OpenBLAS sets aside buffers per thread, about 1 GB committed on 16), the variable taken back once they have, so the spawned worker processes keep a thread per core. Each task's weight is its measured time; events are taken between updates except while the window is built (only the splash repainted there, so no timer reaches a half-built window).
  - `audio_report.py`: the audio setup printed at the start (`[AudioEngine]` lines: the engine that plays and why, the master's device / API / mode / buffer, the headphones' and the booth's outputs, the process's priority, the mixer's switches, MIDI); what the engine then opened follows as its own lines.
  - `window.py`: `AppWindow`, workflow wiring, EventBus wiring, External Sync, metronome, model updates.
- `core/`: shared runtime/state/integration layer.
  - `config.py`: dataclass config schema, defaults, `load_cfg()` (`outputconfig`: the headphones' / booth's output).
  - `os_support.py`: the operating system, detected once per process (its first import: `app.main` at the start, each spawned worker) into flags (`OS`, `IS_WINDOWS` / `IS_LINUX` / `IS_MACOS`, `IS_SUPPORTED`), and the operations that differ by it: elevation (IsUserAnAdmin / uid 0), the taskbar identity and 1 ms timer (Windows only), hidden console windows of child programs (Windows only), revealing a file (Explorer / Finder / the folder via xdg-open), whether another program holds a key as a global hotkey (`hotkey_taken`: RegisterHotKey refused on Windows; not checked elsewhere). The other Windows API users branch on the flags with their fallbacks: the window occlusion check (`utils/window_visibility.py`: user32 + DWM / Qt's exposure), the Python audio engine's scratch cursor poller (`audioengine/python/cursor_poller.py`: Win32 / the GUI's mouse events; the native engine polls the cursor itself, Windows only, else the same mouse events), the physical core count for sklearn (`analyzer_core/utils.py`: Win32 / loky's own).
  - `i18n.py`: the UI's language (Settings > View > Language, `viewconfig.language`, "" = the operating system's; applied at the next start). The languages are `assets/i18n/languages.json` (BCP 47 tags, language-REGION: `en-US`, `ko-KR`, `ja-JP` -> the language's name in itself), each one's gettext catalog `assets/i18n/languages/<tag>/mixlyzer.po`, read as it is (no compiled .mo; fuzzy entries left out). `tr()` / `tr_n()` / `tr_ctx()` translate, `tr_mark()` marks a table's texts (translated where shown); Qt's own texts (standard buttons, file dialogs) come from its `qtbase` catalogs (`install_qt`). Worker processes take the language from the environment (`MIXLYZER_LANGUAGE`). English (US) is the source.
  - `midi.py`: a MIDI controller's mapping, the shortcuts' file convention: the shipped `assets/midi/default_midi.json` (empty) and the user's `assets/midi/midi.json` (gitignored), action id -> messages as rekordbox's CSV writes them ("900B" a note, "B000" a CC, "E000" a pitch bend), options after: H a 14-bit CC (LSB at data 1 + 32), I inverted, a relative encoding O (offset 64) / T (two's complement) / S (sign-magnitude; none: guessed per value), + / - only that direction of a relative control (`Message`). The actions (`ACTIONS`) are a DJ controller's, not the keyboard shortcuts': per deck (`deck{n}.`, up to `DECKS` = 8) PLAY / PAUSE, CUE, track start, tempo slider / range / reset, pitch bend, the jog's mode (JOG MODE VINYL / CDJ, lit in VINYL), touch / top / side / SHIFT search, CUE CALL, JumpCUE pads and their delete, beat jump; per mixer channel (`mixer.ch{n}.`) the fader, EQ HI / MID / LOW, trim, COLOR (its Sound Color FX knob), CUE and the level meter; the crossfader, the headphones' mix and level; the browser (BROWSE knob turned / pressed, BACK, zoom), LOAD, MASTER TEMPO, MEMORY / DELETE; the effects (`fx.`, the Effects group: each Sound Color FX's button and PARAMETER; Beat FX's ON, LEVEL / DEPTH, BEAT down / up, the next / previous effect, TIME, TAP, AUTO, the X-PAD's place and touch, FX FREQUENCY LOW / MID / HI; with their lamps). Each has a kind (button, fader, knob, touch, meter): the engine's code (`code`, the deck's index in bits 24+) or the GUI's actions (`gui`: a knob's per direction), its lamp. Settings shows the `shown` ones only: deck 1, and of the mixer channel 1's fader, EQ and level meter; the others (decks 2-8, trim, channel CUE, crossfader, headphones) are handled by the engine but kept hidden (their mapping is kept on save). The GUI's actions go to the engine as `ACT_GUI` + their place (passed back, run as their shortcuts by `AppWindow._on_midi_events`; a knob's steps repeated). `import_rekordbox_csv` reads rekordbox's MIDI CSV: deck 1's column (a whole message or a channel offset to the input column), mixer channel 1, the global browser / crossfader / headphones rows and ChannelLevel's output, the CFX knobs (`CFXParameterCH1` / `CH2`: the channels' COLOR) and FX1's ON, LEVEL / DEPTH, BEAT down / up, AUTO, TAP and effect select / back (Beat FX plays on the master alone: its CH assigns are left out); other decks are left out.
  - `shortcuts.py`: the keyboard shortcuts' files: the shipped `assets/shortcuts/default_shortcuts.json` (only read; `save` refuses it) and the user's `assets/shortcuts/shortcuts.json` (gitignored; only the actions changed from the shipped keys, a missing file = the shipped keys), both action id -> key sequences in Qt's portable text.
  - `model.py`: shared `DataModel` and `GlobalParams`.
  - `event_bus.py`: Qt signal hub.
  - `workers/`: analysis, segment reanalysis, optimizer, and Rekordbox worker implementations.
  - `workflows/`: Qt-facing worker lifecycle and queue orchestration.
  - `library_handler.py`: SQLite metadata store plus BPM/key segment tables and transition search.
  - `analysis_lib_handler.py`: NPZ feature store keyed by track UID.
  - `external_sync.py`: External Sync (another program's deck followed, received as OSC) / transport lockout; `osc.py` the strict OSC 1.0 decoder it reads with.
  - `player.py`, `timeline.py`, `taskmanager.py`: playback, viewport timeline, worker/task UI state. The deck (the native engine's `src/deck.rs`, or `audioengine/python/deck.py` on the Python engine) takes requests (`EventBus.sig_deck_action`: `client.ACT_*` codes pressed / let go; `sig_tempo_requested`, `sig_tempo_range_requested`, `sig_volume_requested`, `sig_jump_to_requested`, `sig_call_requested`, `sig_deck_marks`) and reports what it is (`DeckReport` through `sig_deck_state`, `sig_playback_status`, `sig_tempo_factor_changed`): the GUI shows the report only, never a transport state it computed (playing, tempo, tempo range, volume, the cue point, the PLAY / CUE lamps, the armed JumpCUE). The native feeder's report waits for every command sent to be taken (`cmd_done`), so a request on its way is not shown undone. `PlayerController` starts the audio engine of Settings > Audio's Audio engine (`playbackconfig.audio_engine`, applied at the next start: "native", the default, falls back to the Python engine where the native one is not built or cannot start; "python" never starts the native one; `player.native` says which plays) and its audio-thread worker drives the engine's feeder (`NativeFeeder` or `PCMFeeder`). Each engine has its own buffer setting (`native_buffer_ms`, default 20; `python_buffer_ms`, default 80): the dialog shows the playing engine's with the rest and the other's under Advanced (`set_audio_engine`). The output device (`output_device`, by the name the playing engine lists: `player.output_devices()`; "" the system's default) changes while playing (a device is found by its name, or the only one of that name but its Windows instance number, "Speakers (2- DDJ-400)" plugged in again as "(3- DDJ-400)": `device::pick`; one not there: the master plays on the system's default meanwhile, a bus on a device of its own (headphones, booth) waits for its device, tried each second, never taking another: `device::NOT_PRESENT`, so a CUE never reaches the speakers and an exclusive stream never locks the master out; a failure said once until it changes, an audio client's code in words: `device::explain`), at the session's format (converted by the system); on the native engine the master goes to a channel pair of it, the headphones and the booth to channel pairs of it or to devices of their own (`set_routing`, below). A scrub's positions reach the engine at most every `SCRUB_INTERVAL_MS` (30 ms, the newest; the views follow the drag itself); the decoded PCM goes to the native engine in a shared block (`client.share_pcm`, `NativeFeeder.adopt` in the decode thread), which is also `DataModel.predecoded_pcm` (no copy).
- `audioengine/`: the player's audio engines. The native one is developed; the Python one is the fallback, kept as it is (its renderer design, `PCMFeeder`'s docs, is what the native one ported): deck 1 on one output, no MIDI, no mixer, no headphones or booth. Audio work goes to the native engine; the Python engine gets only what keeps deck 1 playing as the app expects.
  - `native/`: the default engine, Rust (`Cargo.toml`, `src/`), a process of its own so playback never waits for the GUI's GIL, garbage collector or busy frames (measured: no dropout at a 20 ms buffer with the time stretch, 14 busy processes or the GUI thread holding the GIL). `client.py` is the GUI's side: it makes the control block (shared memory; the layout is `src/ipc.rs`'s and `client.py`'s, keep them together: a sequence-locked state area the engine writes, a command ring the GUI writes, records checked by CRC-32) and starts `bin/mixlyzer-audio --shm NAME --size BYTES --parent PID` (it exits when the GUI process is gone); its console lines (`src/log.rs`, `log_line!`: "[AudioEngine] ...", queued to a thread of their own, so a pipe's busy reader never holds up the engine thread or an output callback) come through a pipe into the app's console, log and startup splash (`client._relay_console`): at the start its version, VOLK, each device opened (API, mode: shared / exclusive event driven / polled, sample format, rate, channels, period, buffer, stream latency, output thread), the threads' scheduling, the MIDI input. `NativeFeeder` has `PCMFeeder`'s methods, `NativeClicks` / `NativeTones` the click and tone mixers' (the metronome drives them); a dead engine is started again with the track and the settings it had, and Settings > Audio > Engine's Restart Audio Engine (the shortcut `playback.restart_engine`, Alt+Shift+E) restarts it by hand, the last resort when an output or the engine stays stuck (`NativeFeeder.restart_engine`: the old one stopped, ended if it does not answer; the track, its place and its play carried over). In the engine (`src/`): `device.rs` the output reading a ring the engine thread fills to the output buffer (a flush fades out over 10 ms in the callback, a raised cosine as every start / stop / seek fade (`dsp::fade_gain`): a linear 4 ms ramp clicked on low notes; before a flush the ring is topped up to two fades past the frame being read, so the fade-out runs whole; stopped off unity with the time stretch, the stream from where play would start is prepared a little each tick (`Standby::Start`), so CUE / PLAY never restart a stream in one tick; device lists are made on threads of their own), through the audio API of Settings > Audio (`native_audio_api`, changed while playing): WASAPI (Windows, `wasapi.rs`: IAudioClient3's low-latency shared stream at the mix format, or with `native_exclusive` WASAPI exclusive in float32 / int32 / 24 bits (in 32, packed) / int16, JUCE's order (the DDJ-400: packed 24), both at the device's smallest period but 256 frames at least (`PERIOD_FRAMES_MIN`, as rekordbox asks the DDJ-400 for: the USB Audio class driver's GetBuffer waits ~0.8 ms each period and now and then 10 ms, which outlasts a 3 ms period, runs the device dry and leaves its events every ~8 ms; measured on the DDJ-400: 132 frames 5 restarts in 80 s, 192 one, 256 none); an exclusive stream is polled: kept two periods full (`POLL_FILL_PERIODS`: the event-driven one's latency; the driver may give a polled stream far more, the DDJ-400 2048 frames, 46 ms, which filled whole was all latency) and topped up every 1 ms, event driven only where the device refuses that (an event-driven exclusive stream whose output thread wakes once a period late runs the device dry, and the DDJ-400's USB Audio class driver then falls back to a 10 ms tick taking one buffer per tick, for good: events 10.00 ms apart at a 5.8 ms period, GetBuffer 0.04 -> 0.75 ms, the device's own play position (IAudioClock) at 58 % of its rate, the headphones a second behind; only Stop / Reset / Start brings it back; measured with the thread held 15, 30 and 60 ms: event driven at 256 frames, rekordbox's way (JUCE's exclusive stream, its buffer one period), fell into the tick at the first hold every time, polled kept 2 periods (11.6 ms), 3 or the whole buffer it stayed at its rate through all three; rekordbox has a polled mode too, off by default: `WasapiPolling`); every stream (the main device's and the others', exclusive or shared) is watched while it runs and started again in place (its bridges refilled) when it is not keeping pace: an exclusive stream's last 8 events 1.8 periods apart on average, the frames it took over a second below 95 % of its rate (events slower than the period without a long gap: the DDJ-400 seen at a 10 ms period taking 64 %, its headphones a second behind), or no event for 200 ms (a second in which the output thread itself woke late is left out: its lateness, not the device's pace); more than 3 times a minute it fails and is opened again by its owner, an exclusive one at the next period of a ladder (256 frames, 512, the device's default, then 256 again: never kept at a period that does not keep pace; `cargo build --features fault` with `MIXLYZER_AUDIO_FAULT=<device>:<from s>:<to s>` makes a device fall behind, tests only); a bridge that keeps skipping a surplus (more than twice in 30 s, any backend) has its device opened again by the outputs' thread; a bridge's reader held up more than three of its callbacks (20 ms at least) starts again as at a restart (filled to its buffer, its loop settled anew: followed on, the catch-up was taken for drift, 1000 ppm for tens of seconds); the `fault` build also records a device's events (`MIXLYZER_AUDIO_PROBE=<device>`: wake-ups, driver call times and its IAudioClock position to %TEMP%/mixlyzer-probe-*.csv), holds its thread once at given times (`MIXLYZER_AUDIO_STALL=<device>:<s>:<ms>,...`), leaves a stream not keeping pace as it is (`MIXLYZER_AUDIO_NO_RECOVER=1`) and picks its polling (`MIXLYZER_AUDIO_POLL=<device>:<periods>`, 0 event driven; `MIXLYZER_AUDIO_POLL_FILL=<device>:<periods>`, the level kept, 0 the whole buffer; `MIXLYZER_AUDIO_FORMAT=int24/24,...` only those formats tried; `MIXLYZER_AUDIO_QUERY=<device>` an event-driven stream's padding asked for every 1 ms between events). Why the polled stream survives where the event-driven one does not, seen on the probe: a late wake-up lets the device play one buffer that is never written back (event driven writes one buffer per event), so the driver is left with one buffer in flight and falls into its tick; polled, the next wake-up writes what is missing at once. The padding queries alone (no earlier writes) did not save the event-driven stream; rekordbox's own DDJ stream is fed by a thread that never sleeps, querying the driver in a loop (sampled: its syscalls the same as our polled thread's), so it refills at once too; at `native_exclusive_rate` when set: the session's rate, so it is applied at the next track load, `NativeFeeder.apply_session_format` starting the engine again after the old one let go of the device), WASAPI (cpal) / ALSA / CoreAudio (cpal's output; ALSA and CoreAudio with a ~5 ms device buffer) or JACK (Linux: cpal's JACK host); one that does not open falls back to cpal's (WASAPI's usual stream: ~32 ms). The buffer kept is the setting (2 ms and up; the engine thread ticks every 1 ms below 10 ms) plus what the device takes at once (`Ring.max_frames`), and the output callback wakes the engine thread after each read (`Ring.engine_thread`), so the ring is topped up before the next period. Commands carry the GUI's send time (protocol 2), and the engine measures play / pause / seek to the moment their sound is heard by the device's clock (the meter's "Response measured"; the driver's reported latency included, not the DAC's), The buffer monitor's histogram has 0.1 ms buckets up to twice the capacity (wider for big buffers), the lowest level over 10 s is the engine's own, and the dialog shows them in µs with a histogram (`ui/buffer_histogram.py`; the Python engine's in ms, 1 ms buckets). At a small buffer the time stretch stays fed: each tick fills the ring before the standby stretcher's work, which takes at most 30 % of the buffer's time a tick (one step at least), and a scrub let go resumes the tempo 80 ms ahead, its stream prepared meanwhile, at that very frame (no restart in one tick), `engine.rs` PCMFeeder's port (the timeline, the standby stretcher, jumps, scratch, the buffer monitor), `stretch.rs` the time stretch (its FFTs on realfft / rustfft, its vector work on VOLK through volk-rs: `vk.rs`), in two modes: the full one (`Stretcher::new`: the Python one's spectrograms, about a third of its CPU; `--stretch-file`'s default, which tests/test_native_engine.py compares with the Python engine) and the light one the engine plays (`Stretcher::light`, about 40 % of the full one's work: 2.1 % of a core at 48 kHz against 5.5 %): the band split of `split.rs` (the low band decimated by 3 at 44.1 / 48 kHz, by 6 at 88.2 / 96 kHz, a Kaiser lowpass -90 dB from its Nyquist frequency, the passband to 7/8 of it: 7 kHz at 48 kHz; the high band the residual, so the bands sum to the source; both computed where they are read, a few windows cached: no memory per track), the phase vocoder on the low band only (a third of the bins; its RTPGHI's heap a bucket queue of 1/8 octave, `rtpghi_frame_buckets`), synthesised at the full rate by a zero-padded inverse FFT; the high band by WSOLA on the vocoder's own frames (one time map for both), looking within 5 ms for the segment that continues the last (by FFT cross-correlation; within 0.5 ms a synth's or a voice's high harmonics warbled), its splices' level kept whatever their correlation; each event's attack the source's own: its onset found in the source (`onset`) and carried to its destination on the time map, the high band and the vocoder's band above 200 Hz crossfaded to the source's there (`restore_light`: a 1 ms rise ending before the attack, the plateau ending where the attack has decayed 9 dB and the source and the stretched output agree best, a fall of 2 - 8 ms by their correlation, the level kept whatever it), so every band's attack lands at the same time and none is overlap-added; the bass below 200 Hz keeps its own phase (crossfaded with the source's it cancelled); below 28 kHz the full mode; `dsp.rs` varispeed / read_at / the platter (bit-identical to the Python ones), `mixers.rs` clicks and tones, `cursor.rs` the 1 kHz cursor poller, `clock.rs` the clock both processes share (Python's `perf_counter`). The engine thread runs every 2 ms (1 ms while scratching). Its threads' scheduling is `sched.rs`, from Settings > Audio's priority (`native_priority`, High by default) and power throttling (`native_power_throttling`, off by default), sent at once (`op::SET_PROCESS`, replayed at each start), what was got published (`st::THREADS` / `st::POWER`, shown under the meter): Windows the engine thread and its own WASAPI thread MMCSS Pro Audio and the 1 ms timer always, the setting the process's priority class and EcoQoS / timer coarsening opted out; Linux per thread (the engine's and the ALSA output's, its thread id written by the callback; a thread already real-time, JACK's, is left alone): High SCHED_FIFO, else rtkit's MakeThreadRealtime (zbus; RLIMIT_RTTIME set to rtkit's limit, SIGXCPU drops the thread to SCHED_OTHER), else nice -10 (Above normal -5; else rtkit's MakeThreadHighPriority), power throttling off a 1 ns timer slack (each thread sets its own) and uclamp's minimum at the top; macOS the engine thread High a time-constraint thread, Above normal QoS user-interactive, Normal QoS default (CoreAudio's thread is its own), power throttling off a latency-critical NSProcessInfo activity (objc2). The native engine is developed and measured on Windows; on Linux and macOS it is experimental (cross-checked with `cargo check --target`, not run there yet), and the dialog and the READMEs say so. The WASAPI thread counts its late wake-ups (a gap over 1.8 periods: shown under the meter), and the engine writes the last ticks before each gap (an underrun or a late output wake-up) to `%TEMP%/mixlyzer-audio-trace.log` (2 MB at most). Its buffer setting is this engine's own buffer, ahead of the device's latency (shown beside the meter; measured here: exclusive 6 ms, low-latency shared 12 ms, cpal's shared 32 ms), and the meter's dropouts are the engine's underruns. While scrubbing the time stretch plays the original at unity (a stream restart, ~10 ms of work, per drag position would not keep up), released it takes the tempo at once; seeks queued in one tick are made once (the last); a seek or a jump while playing off unity goes through the standby stretcher, prepared 1.5 ms of work a tick. `--stretch-file` (`--light`: the light mode) / `--scratch-file` render offline (tests/test_native_engine.py compares the full mode's with the Python engine and checks the light mode's level and attacks, every band's on the time map).
  - Its decks (`src/deck.rs`): up to 8 (`ipc::MAX_DECKS`), deck 1 always there, the others made when first addressed (a controller's message or `op::FOR_DECK`: deck, op, payload; deck 1's GUI player sends plain ops, another deck's `NativeFeeder(deck=k)` wraps its deck ops (`DECK_OPS`) and reads its report row; settings like the time stretch go to every deck, sent by deck 1's player), each its own engine (`Engine`: track, timeline, stretcher, channel strip) and lanes. Each deck is one place for the GUI's requests and a MIDI controller's, combined in the engine thread: rekordbox's CUE (stopped off the cue point: sets it on the nearest beat or track edge; held on it: plays until let go, PLAY while held plays on; playing: back to it and stops; a CUE point's CALL moves it there), beat / bar steps, CALL previous / next, a JumpCUE's JUMP (armed on the next beats, the GUI's former logic), the tempo with its range (6 / 10 / 16 % or WIDE, 0 - 200 %; a range change keeps the tempo inside the new range), the volume fader (utils/volume.py's curve, ported; the channel's TRIM knob is the level before it), the jog wheel (its mode: VINYL, or CDJ where the top's touch is ignored and a turn only bends; `act::JOG_MODE` a press, `MIDI_OPTIONS`' second u32, every deck's, a deck made later's too; DeckRow lamps bit 2, `LAMP_VINYL`; touch: the platter at a 20 ms delay, both rotation CCs move the record while it is held; let go while the platter turns, it is followed on until no message for 50 ms, as rekordbox's backspin; scratch 33 1/3 rpm by `midi_jog_ticks` a turn; bend: a turn a second +10 %, eased out over 80 ms; search), the lamps (PLAY lit playing else blinking; CUE lit playing / previewing / on the cue point else blinking; a JumpCUE's pads, JUMP and its SHIFT delete, lit while it is set and blinking while armed; each binding carries its lamp, `core.midi.lamp`; sent to the controller's output of the same name, only those that changed), the level meter (`midi.level_meter`, an output CC: the GUI peak meter's reading, the heard peak times `SET_METER_GAIN`, -24 - 0 dBFS as 0 - 127 falling 24 dB/s, at most every 20 ms; the rekordbox import takes it from ChannelLevel's output column). At the track's end the deck plays on (silence, on either engine): dragged or moved back, it plays again from there. `src/midi.rs` reads the controller with midir (WinMM, ALSA, CoreMIDI) on its own thread, which wakes the engine thread per message (its ports listed, opened and closed on threads of their own: tens of ms each, never the engine thread's; the port open or being opened asked for again is kept, and an open waits for the last close: WinMM refuses a port still being let go, MMSYSERR_ALLOCATED); `src/controller.rs` decodes them in the engine thread (relative encodings, 14-bit CCs, pitch bend, a direction's binding fired per step) to the deck addressed, the mixer's controls to `MixParams`, and sends the lamps and level meters; the messages bound to the GUI's actions (a JumpCUE pad's empty slot flagged as a SET), and all while Settings > MIDI learns, go to the GUI through a ring (`ipc.rs` MIDI_EVENTS; `NativeEngine.midi_events`). MIDI is the native engine's alone (the Python engine has none; External Sync closes the port). The signal flow is player -> mixer strip -> mixer. Each deck's player (`engine.rs` `Engine`) renders its track alone into its lane (`device.rs` `Bus`: a ring per deck with its own flush fade and timing; deck 1's the `Ring` itself), a lane frame [music (ch), aids (ch)]: the listening aids (the metronome's clicks, ducking the music under them; reference tones) beside the music. The mixer (`src/mixer.rs`, a DJM-A9's but its mics, SEND / RETURN, LINK CUE, QUANTIZE and CENTER LOCK: they need inputs, a grid or a knob's touch the engine has not) runs in the main output's callback, so a fader, a knob or a CUE is heard after the device's latency alone, not the engine's buffer. Each channel's strip (`Strip`; its settings `StripParams`, atomics the deck sets): trim -24 - +9 dB (Settings > Audio's trim is the TRIM knob: `NativeFeeder.set_volume_trim`), Sound Color FX (`colorfx.rs`: SPACE, DUB ECHO, SWEEP, NOISE, CRUSH, FILTER, JET (a DJM-800's: a flanger's comb turned by hand, 6 to 0.12 ms, right in phase, left inverted, PARAMETER its feedback) or none, picked for the mixer, the channel's COLOR knob, the PARAMETER knob as the A9 manual's pages 38 - 41 give it), a 3-band EQ (`ipc::mix::EQ_MODE`: an isolator, Linkwitz-Riley 4th order at 246 Hz / 2484 Hz, a band from kill to +6 dB, or an EQ, shelves at 70 Hz / 13 kHz and a 1 kHz peak, -26 - +6 dB), its meter (pre-fader: the GUI's peak meter and a controller's level meter, held 50 ms by the engine) and its pre-fader CUE taps (headphones A and B), the channel fader (the deck's volume, three curves), the aids added after it all. A stopped deck's strip runs on silence while an effect after its fader rings out. The main callback, the clock the decks play to, writes the bus into a bridge (`src/bridge.rs`), which the other device's callback reads at its own clock and rate: across the clock domains it resamples by the rates' ratio times the clocks' drift (a PI loop on the bridge's level as zita-ajbridge reads it: each side's device play position, stamped, and its mean queue (the writer's before its writes, the reader's after its reads: the level held is the bridge's lowest at any phase of the two periods), so neither the periods nor a shared stream's topping-up saw it; after 3 s settling the level the fill left is held, then moved to the buffer at 0.5 ms/s fed forward (a new buffer setting the same way), so the integral is the drift alone; a level more than 0.1 s over the buffer itself (the reader held up while the writer went on, also while it settles) is skipped at once, never held; the drift within 1000 ppm; a 64-tap Kaiser-windowed sinc interpolator, error under -85 dB to 20 kHz, to a lower rate cut at the output's Nyquist frequency: nothing repeated or dropped). ## App Flow
- Entry is `app.main:main()`.
- On startup the app:
  - makes the app folder the current folder (`core.resource_paths.app_folder`: the package folder in a build, else the project root), whatever folder it was started from: `config.json`, the library and the caches are always the app's, and no program or `config.json` of another folder is taken,

  - shows the startup splash (`app.startup`),
  - loads `config.json` (warning when it could not be read and was kept aside),

  - checks the on-disk library version through the migration adapter and stops on a mismatch,

## Analysis Flow
- A load onto the deck (a drop on the deck, the library's load: `sig_request_load_track`, External Sync) goes to `AppWindow.load_track`: the file plays at once (decoded; a new file shows its tags meanwhile and the decoded length) and `AnalysisWorkflow.analyze(path, listener=)` gives the deck its features (a library track's stored ones at once, a new file's when analyzed: the analysis's results alone are applied then, `DataModel.load(keep_audio=True)`, the playback goes on; applied only while the deck still holds that file). A file only analyzed into the library (dropped on the library, a playlist's new files, Reanalyze on files not analyzed yet) goes by `sig_request_analyze` (no listener; a library track's is not analyzed again).
- Full-track analysis runs in a spawned subprocess via `core.analysis_worker.AnalysisWorker`. The process runs with one BLAS thread (`threadpool_limits` in `core/workers/analysis.py`): the analysis runs its own threads, and BLAS threads on top only competed (the outputs are the same; a track about 20 % faster, a third less CPU).
- The worker calls `analyzer_core.global_analyzer.precompute_features(...)`.
- Current pipeline in `global_analyzer.py`:
  - decode/load audio,
  - HPSS split (always on, not a setting; its median filters are a sliding median kept sorted, `analyzer_core/dsp/running_median.py`, equal to scipy's `median_filter` and several times faster),
  - overview waveform (its own 48 kHz decode: min / max of 32768 columns, the power of 12 log-spaced bands in 8192 columns, and the detail waveform's three-band scale),
  - beat tracking (`analyzer_core.beat.general.track` on the frame features; frames on the fixed grid `frame_features.FRAME_HOP_LENGTH` (256); the models were trained on 22050 Hz HPSS frames; every analysis runs at 22050 Hz (`core.config.ANALYSIS_SAMPLE_RATE`, not a setting) with HPSS, so the tracker reads the analysis's own frames): per training seed, tempo candidates from the activation's periodicity -> section decoding into steady (tempo, phase) grids with one section cost -> exact tempo / phase fit -> sudden vs gradual tempo changes (linear ramps, continuous or with a jump at one end) -> bar-supported half-beat phase (bars of 2, 3 or 4 beats) -> metronome critic (3:2 / 4:3 misreads) -> tempo-change boundaries on the refine onset -> slow tail held -> drifting sections -> tiny re-syncs merged -> junction rules (no too-close / too-far beats at grid changes) -> bars (a Viterbi over 3- and 4-beat bars on two downbeat observers; an odd bar costs, a new section starts free); then the seed whose grid agrees most with the other two. Every tempo is read in the octave from BPM min. The rows have `inizio` on a downbeat and `ts` the bar length (`bars.to_rows` splits a row where the bar length changes), so the segments always rebuild the beats and downbeats,
  - JumpCUE detection,
  - key analysis (`analyzer_core.key.chord_key.analyze_keys` on the beats, the downbeats and the phrase starts; no keys when it fails),
  - persistence to SQLite (`LibraryDB`) and NPZ (`FeatureNPZStore`).
- Cached-track loads can skip analysis and load metadata/features directly from `library.db` + NPZ.
- Reanalyze-track requests (`sig_reanalyze_requested`: the path and analysis settings for this run only, or None) force a fresh full analysis and overwrite stored results.

## Segment Reanalysis
- Partial reanalysis is orchestrated by `core.segment_reanalysis_manager.SegmentReanalysisManager`.
- Work is offloaded to a subprocess via `SegmentReanalysisWorker`.
- Supported modes currently include:
  - beat segment reanalysis,
  - static key selection reanalysis (`chord_key`: the key with the most evidence over the selection),
  - dynamic full key reanalysis (`chord_key` on the editor's current beatgrid, bars and phrases),
  - JumpCUE reanalysis (with AutoCUE on JumpCUEs, the AutoCUE JumpCUE goes where the editor's current phrases' lead-in ends; with AutoCUE on CUE points, the Phrase page's CUE button places it),
  - phrase reanalysis (the whole track on the current beatgrid; the CUE points stay).
- Results are pushed back into the in-memory `DataModel` and editor widgets; they are not a separate analysis system.

## Data & Persistence
- Track metadata lives in `library/library.db` in the `tracks` table, keyed by `uid` (PRIMARY KEY, canonical UUIDv4).
- `track_readings` (uid, field, slot) holds the romanized readings of each track's title / artist / album (`core.reading`): the search's intermediate representation, up to 7 a field, each with its source (ja, zh, yue, ko-hanja, vi, zh-tw, ko, text, or user). The readings the user added (Edit Track's Readings grid: only the cells typed there; source `user`) are kept and come first; the automatic ones after them are made anew in the stored languages whenever the track is written (`LibraryDB.upsert` -> `refresh_readings`, `library_handler.field_readings`), so a language unchecked removes only automatic readings. An automatic reading the user removed (emptied, Delete, or typed over in the grid) is kept in `track_reading_removals` (uid, field, reading) and left out from then on, whatever the languages; typed again, it is the user's. Settings > Search's Re-read Library (also started when what the stored readings depend on changes: `searchconfig.stored_readings()`) reads every track again in a spawned process (`core/workers/reading_refresh.py`, `core/workflows/reading_refresh.py`; 50 tracks a transaction, the library reloaded when done). The library's text search matches Title / Artist / Album by these too.
- Playlists (`playlists`, keyed by their own UUIDv4 `uid`) hold one `playlist_tracks` row per entry, (`playlist_uid`, `position`) -> `track_uid`: a track may be in a playlist more than once, so the UI addresses an entry by its position (reorder / remove), never by the track. Removing a track removes its entries and closes the playlists up.
- BPM and key transitions are also persisted in:
  - `track_bpm_segments`
  - `track_key_segments`
- Tempo segments are rows `[start, end, bpm, inizio, ts_num, bpm_end]` (`core.tempo_rows`). A `bpm_end` that differs from `bpm` is a linear tempo ramp (tempo linear in time from `start` to `end`; its beats come from the closed-form phase); rows without it (5 columns, older data) or with it equal are steady. `inizio` is a downbeat on the row's own grid. `track_bpm_segments.bpm_end` mirrors it (NULL = steady): transition search reads a ramp as a change from its start to its end tempo, and a phrase section inside a ramp gets the tempo at its midpoint. The editor keeps ramp rows (cut / merge / shift follow the tempo line; Assign makes the row steady at the reference BPM; the ramp start / end buttons make the reference BPM the row's start or end tempo, its first beat kept), and the Rekordbox export (which has no ramps) writes a ramp as steps of steady tempo, one TEMPO entry each: a step per beat, or several beats while every beat stays within Settings > Library's Tempo ramp tolerance (`libconfig.rekordbox_ramp_tolerance_ms`, default 1 ms), measured as written (Inizio in ms, the BPM rounded down to 0.01 so a step never puts a beat just before the next one's).
- Numeric feature arrays live in `{libpath}/{uid}.npz` through `FeatureNPZStore`. Only what is read is stored: beats, tempo/key segments, the overview waveform (`wave_minmax_np` / `wave_minmax_ref`, `wave_bands_np` / `wave_bands_ref`, `wave_detail_band_ref`), duration, sr, tempo_global, and the JumpCUE / CUE point / phrase blocks. Saving replaces a block as a whole (`save_worker._replace_block`).
- Track identity across DB, NPZ, thumbnails and playlists is the `uid`; the file path is an editable attribute (`LibraryDB.set_path`; the track panel's Edit tab). `tracks.path` stays UNIQUE (one file, one track).
- `tracks.path` is stored as given, never normalized (case / separators can name different files on other file systems). A path that may spell a library file differently (a drop, External Sync's deck path) is looked up by the file it opens (`LibraryDB.find_file`) and then used as stored.
- A library track whose file is missing is not loaded: the app says so and asks the user for the file's new location (no guessing by name or content).
- `track_tag_sources` (uid, field, slot) holds where the track's file holds its title / artist / album / comment (`core.audio.tag_writer` spellings, as `vorbis:PERFORMER` or `mp4:titl`; one row with source "" when none does: a title from the file name, a field read empty): recorded by the analysis when it reads the tags (`global_analyzer.read_tag_sources`: the spellings holding the values read). The analysis reads the tags and the cover with the app's own readers, no native tag library (an outside file): `tag_writer.read_fields` / `read_picture` for FLAC / MP3 / AAC / WAV / AIFF / MP4 (MediaInfo's order of places, `LEVELS`; the cover the front one, else the first), FFmpeg for the other formats (`decoder.read_metadata` / `read_cover`); the cover is decoded by Qt in the format its first bytes name (JPEG, PNG, GIF, BMP, WebP), at most `COVER_MAX_BYTES`, used by the Export tab's File Tags to write each value back there. BPM and key are not read from the tags (the analysis gives them), so they have no source: they are written to the format's own places. A track without sources (added before they were kept, or given another file: `set_path` clears them) gets them found from its file on its first write.
- Album art thumbnails (downsampled, JPEG) live in `{libpath}/thumbs/{uid}.jpg` (`core.thumbnails`): written by the full analysis, removed with the track; the library table shows the top of each as its first column.
- The key strip is rendered just in time from `key_segments` (`utils.keystrip.render_keystrip`); no image is stored.
- The overview waveform and the main view's preview (its stand-in until the detail chunks are drawn) are rendered just in time from the stored overview (`utils.wave.render_wave_overview` / `render_wave_detail_preview`) in the style of `viewconfig.waveform_style` (RGB, or rekordbox-style 3Band; the overview's bar heights are the bands' power in both, stacked with the 3Band weights: RGB one bar coloured by the band mix against the track's usual balance (`wave.overview_colors`: each column's colour first: each band over its median where the track is audible, so the phrases come out in different colours; cubed, so the band clearly above its usual level leads the colour; red / green / blue for low / mid / high over the strongest as Mixxx's and rekordbox's RGB waveforms; in OKLab one lightness, moved by the brightness: the spectral centroid of the 12 bands against the track's usual one, darker towards the low band's red, brighter towards the high band's blue (a filter sweep inside one range shows); then smoothed in hue over 0.5 s, so it does not flicker: the mean colour's direction and the mean chroma apart, so hues taking turns within a beat never average to grey; the chroma at least the most every hue holds at that lightness; silence neutral), 3Band the bands stacked in their colours; the preview keeps the min / max): low / mid / high are summed from the 12 stored bands with the ranges of Settings > View > Waveform bands (`viewconfig.env_*`, weighted by log-frequency overlap), so a change of the ranges redraws them at once without re-analysis; no image is stored. The detail waveform is rendered from the playback PCM (its three-band scale is the stored `wave_detail_band_ref`). Libraries analyzed before this format are converted by hand with `migration/wave_overview_bands.py`.
- JumpCUEs are kept in two states in the NPZ: `jump_cues_np` (the user's, replaced by edits) and `jump_cues_auto_np` (the automatic result, replaced only by full analysis or JumpCUE reanalysis). The JumpCUE optimizer (settings → Analysis → CUE) learns from where they differ; do not write edits into `jump_cues_auto_np`.
- A JumpCUE group's colour is a preset index (`graph_color_idx`, presets in `utils/jumpcue_colors.py`), independent of its group number (`graph_id`); no RGB is stored. Edits carry it on each cue as `color_idx`.
- Keys are kept in two states in the NPZ like the JumpCUEs: `key_segments` (the user's, replaced by edits) and `key_segments_auto` (the automatic result, replaced by the full analysis and the editor's whole-track key reanalysis, saved with the editor's next save). The key optimizer learns from the tracks where they differ; do not write edits into `key_segments_auto`.
- CUE points (`cue_points_np`, with a colour preset `cue_color_idx`) are the user's: the full analysis makes them from the phrases by the per-label rules in `config.cuepointconfig` (Settings > Analysis > CUE; LEAD_IN has no rule), after that only the CUE page edits them (phrase edits do not regenerate them), or the Phrase page's CUE button replaces them with what the same rules give the current phrases.
- Phrases cover the track when read: stretches without a stored phrase (all of a track analyzed without phrases) are `UNASSIGNED` (`utils.phrases.fill_unassigned`). It is shown and edited like a label but never stored (`assigned_phrases` on save), so it never reaches training data.
- Phrase labels are the fixed `utils.phrases.PHRASE_LABELS` (no custom labels). How each is shown is a setting (Settings > View > Phrase labels: an alias and an overview abbreviation, empty = the label / its first letter), applied through `utils.phrases.set_phrase_label_names`; stored data always keeps the label itself.
- JumpCUE letters are slots (rekordbox hot cue letters A-Z): the analysis letters them by point; edits keep each cue in the slot the user gave it (no relettering by time). A JumpCUE's user name is its `cue_comment` (equal to its letter = no name). CUE points are rekordbox memory cues: always in time order, no letters; a CUE point's name is its `cue_label`. The Rekordbox XML writes them as memory cues (`POSITION_MARK` `Num="-1"`, with their colours) and the JumpCUEs as hot cues.
- `DataModel` holds the live in-memory track state:
  - `features`
  - `properties`
  - `duration_sec`
  - `gp`
  - `album_art`
  - optional predecoded audio buffers

## UI Notes
- `ui.pane.MainPane` owns the top-level plot stack, overview, track info, transport controls, editor panel, and library widget. The transport column is stop, a yellow CUE (an icon, `assets/icons/transport_cue.png` / `_lit`; pressed and let go both sent; lit / blinking as the deck reports its lamp) and play; the tempo fader's steps follow the reported range (6: 0.02 %, 10 / 16: 0.05 %, WIDE: 1 %), the range button (its text the range, WIDE included) is the column's head in place of a Tempo label. The faders send requests and show the reported tempo / volume (not while the hand is on them). Right of the peak meter the player's channel knobs (`TrackInfoPanel.knobs`, `ui/knob.py`), top to bottom as a DJ mixer's: TRIM, HI, MID, LOW; turned they send `sig_knob_requested` (TRIM: the trim on either engine, `utils.volume.TRIM_DB_RANGE` -24 - +9 dB; the EQ: the native engine's mixer, disabled on the Python engine) and they show the reported knobs (`DeckReport.knobs`; the Python deck reports its trim). The trim the deck reports (its knob, the settings, a controller) is kept as Settings > Audio's trim (`AppWindow._keep_trim`: the peak meter's gain and the settings' field at once, `config.json` a second after it last moved), as the tempo range is. The editor sends its beats, downbeats, CUE points and JumpCUEs to the deck when one of them was replaced (`EditPanel._send_deck_marks`, checked every 100 ms).
- Analysis views are plugin-like classes from `views/` instantiated via `REGISTRY`.
- The main plot's lanes (`views/base.py`), bottom to top: the key strip, the phrase band, the waveform, a top margin for the JumpCUE blocks / CUE point markers. The deck's cue point (as reported) is an orange triangle pointing up, its base on the phrase band's top (`views/deck_cue.py`). The playhead's bar.beat label sits left of it at the top; the beatgrid's tempos are labelled at that height (`views/tempo_label.py`, installed with the beatgrid display, its emphasis the beatgrid page's) as the key and phrase labels are: each comes in at the beat nearest its tempo's start (a tempo changes at a beat; the row's edge can sit between), is held right of the playhead while that tempo plays and is pushed along by its end, dimmed from when the next tempo's label touches it on (faded over the last pixels before; passed, it stays dimmed); `174 BPM` (neighbours with the same tempo joined: a row split for its bar length is no change of tempo), a ramp's `rit. 180→160 BPM` / `accel. ...`, and while the playhead is in it the tempo there, `rit. 172.4 BPM`; outlined like the bar.beat label, at z 12: just above the beatgrid's lines (10, 11), under the CUE markers (105, 110), so it never hides a cue.
- The main view's detail waveform (`views/waveform.py`) is rendered from the playback PCM in 1 s chunks on its render thread (`_WaveformRenderWorker`, `RENDER_BATCH_SIZE` at once, one started every `RENDER_SPAWN_INTERVAL_MS`): the pending chunk nearest the playhead starts first (ahead before behind at one distance); a scrub let go or a seek drops the requests made on the way and starts the chunk playback goes on from at once (on a thread of its own when the slots are busy). Chunks farther than `RENDER_KEEP_SEC` from the playhead are dropped, except the ones shown most recently (`RENDER_RECENT_KEEP_SEC` of them over all layers). The thread is stopped at `detach` and when the app quits (`aboutToQuit`): the views are freed after `app.exec()` returns, and a QThread destroyed running aborts the process.
- Edit focus: while the edit panel is unlocked, the main view and the overview emphasize the visualizations of the pages shown (lines thicker, markers larger) and dim the other pages' (`EventBus.sig_edit_focus_changed`, a frozenset of `views.base.EDIT_PAGES`; a view declares its page as `ViewPlugin.EDIT_PAGE` and styles its items in `_apply_emphasis`, also after creating items; the overview in `OverviewWidget._apply_emphasis`). Shapes and colours stay; the waveform and the playhead belong to no page.
- Enabled views come from `viewconfig`:
  - waveform
  - beatgrid
  - keystrip
  - JumpCUE
- `ui.library.LibraryWidget` is not just a browser:
  - its table rows are made when the source changes; a library update (`sig_lib_updated`, several in a row applied once after `LIBRARY_UPDATE_DELAY_MS`) changes only the rows of the tracks added / changed / removed (up to `INCREMENTAL_ROWS_MAX`, else the table is rebuilt), and the search and filters hide rows (applied once they pause, `SEARCH_DEBOUNCE_MS`); actions use `_selected_rows()`, which leaves hidden rows out (Ctrl+A selects them too),
  - it performs text search,
  - transition search using DB segment tables,
  - remove/reanalyze/edit/export actions: removing asks first (No by default); reanalyzing analyzed tracks opens `ui/reanalyze_dialog.py` (BPM min, dynamic beat / downbeat / key, AutoCUE) whose values are this run's only: the ones differing from the saved settings ride `sig_reanalyze_requested` to `AnalysisWorkflow.reanalyze(path, analysis)`, which runs the worker on a copy of the config with them (config.json untouched),
  - the track panel under the search, right of the track list and as tall as it: Edit / Export tabs on a thin vertical tab bar at the far right (clicking the open tab folds the panel to the bar). Unfolded, it shows the selected track, following the selection once it rests (`PANEL_FOLLOW_MS`); the Edit tab's changes not applied are asked about before another track is shown (`EditTrackPanel.has_changes`). The context menu's Edit Track / Export Track (and their shortcuts) unfold its tab and move the focus into it; Esc goes back to the tracks.
- Keyboard shortcuts (`ui.shortcuts`): the shipped keys follow rekordbox's (Performance 1 preset, deck 1: Z play, Shift+A back to the start, R / T call the previous / next memory cue, 1-8 hot cues, Ctrl+Shift+1-8 clear them, Shift+Left load, Alt+F search, Shift+5 master tempo, = / - zoom) where Mixlyzer has the function, in three tiers: no modifier (Shift / Alt variants included) changes no data (playback, the playhead, the library's selection, the editor's pages (F1-F4) and lock (L)), Ctrl changes the data in memory (the editor's edits; Ctrl+Z / Y / S; a new playlist), Ctrl+Shift destroys data (deleting a cue, removing tracks, a full reanalysis, writing the file's tags). Every action has its own keys. An operation several editor pages have and that is the same on each (a key / phrase boundary earlier / later, split, merge, reanalysis of the current segment / the whole track, the edit scope, the boundary step) is one "Current page" action done on the current page (`EditPanel._context`: the page shown; with pages side by side the one picked (F1-F4) or clicked last, marked in the selector: its title lit (4 shown) or its name lit on its pair's button and the other's dimmed (2 shown)); one operation per key, never a different operation by page. A momentary action (`Action.momentary`: CUE, key A) gets True when its key is pressed and False when it is let go (or the app loses the focus). The playhead's beat / bar steps repeat while their key is held at their own rate (`Action.hold_rate`: 8 / 4 a second, a timer from the press until the key's release or the app losing the focus), not the system's key repeat (the beatgrid shifts, BPM x2 / x1/2 and the key's semitones are their pages' own). A page's own tool shows its page (and the CUE list page holding its slot), which becomes the current page. Either way the button is worked as the mouse does (`EditPanel._shortcut_click`) and flashes (`ui/edit_panel/flash.py`: an accent glow drawn over the button, its style sheet untouched); an edit while editing is locked does nothing and the status bar says why. Plain navigation keys (Up / Down / Page / Home / End; plain Left / Right in a tree) go to a focused list, spin or combo box instead (typed characters already go to a text field); Up / Down from the search field move the library's selection. The sources panel beside the library (`_LibrarySourceTree`): Alt+S goes there and back; moving with the keys only highlights a source (a click still opens it), the load key (Shift+Left) shows the highlighted one and returns to its tracks; Esc leaves the search field (its text kept) or the sources panel for the tracks. Settings > Shortcuts shows each action by a short name, its details in the tooltip (`Action.tip`). A key another program holds as a global hotkey never reaches the app (graphics card overlays: NVIDIA / AMD hold Alt+R, Alt+Z, Alt+F1 / F9 / F10, Ctrl+Alt+R / M, F12 ...): Settings > Shortcuts marks such keys and asks before assigning one, the start says which assigned keys are held (`os_support.hotkey_taken`), and the shipped keys avoid them.
- `ui.export.ExportTrackPanel` prefers the in-memory `DataModel` for the currently loaded track and falls back to NPZ when needed.

## External Sync
- `core.external_sync.ExternalSyncController` follows another program's deck: the track it has loaded and its position, received as OSC over UDP (`OscReceiver`, its own thread keeping each deck's newest state; the GUI takes it at the view's frame rate), one message per deck: `/mixlyzer/deck/time  i deck s path T|F loaded T|F active d|f seconds` or `/mixlyzer/deck/samples  i deck s path T|F loaded T|F active h|i samples i rate` (rate 0: the file's own; a flag may be an i 0 / 1). The deck followed is the lowest-numbered loaded and active one; a deck silent for `STALE_SEC` is gone. Settings > External Sync: on / off, the address and port (127.0.0.1:39321 by default), the status, the message format.
- It listens on this computer only unless the settings name another address; then only library tracks are followed (no analysis started from the network). A path must be a local file: UNC / `//host` spellings refused before and after a link is resolved (opening one sends the user's credentials). Packets are parsed strictly (`core.osc`: lengths checked, only i h f d s T F, 8 KB at most) and refused whole when malformed.
- Mixlyzer reads no other program's memory. The memory reader that used to be here is its own program, the External Sync bridge (github.com/hygn/Mixlyzer_extsync): it reads a DJ program's deck state through the user's pointer chains and sends these messages. The user's chains live in that bridge's git-ignored `bridge.json` and are never committed to either repository (local pre-commit / pre-push hooks refuse them).
- When enabled, local playback/load controls are intentionally restricted.
- If you touch External Sync config or behavior, keep `core/config.py`, `ui/config/`, and `app/window.py` aligned.

## Change Guidelines
- Keep heavy DSP, file IO, and long-running work off the GUI thread.
- Worker subprocess entry points must remain module-level pickleable callables. Do not pass Qt objects into multiprocessing workers.
- When changing config shape/defaults:
  - update dataclasses in `core/config.py`,
  - update `default_cfg()`,
  - keep `config.json` compatibility in mind,
  - update `ui/config/`,
  - update any call sites assuming the old fields.
- When changing persisted analysis outputs:
  - update readers in `DataModel`/UI/views,
  - update DB segment adapters in `core.linear_segments` if segment schema changes,
  - consider migration needs for existing libraries.
- `library/` is user data. Do not delete, reset, or commit its contents.
- Preserve `uid` linkage between SQLite and NPZ when editing library code.
- Analyzer speed-ups keep every output bit-identical: compare each output array of a few library tracks before and after (in fresh processes, the user's config.json), and replace a loop by a compiled one (numba, with the Python path as fallback) only where it does the same float operations in the same order (the phrase GBM's trees, the downbeat features' small medians).
- Learned models are shipped as `assets/weights/default_<name>` and the settings name the user's `<name>` (missing = the shipped one: read through `core.model_files.resolve_model`); every optimizer calls `optimizer.model_start.check_output`, so Reoptimize never writes a shipped file (the phrase and JumpCUE models too), and the spec bundles the `default_` files only.
- Files the app reads may come from elsewhere (audio, models, caches, a library): never pickle (NPZ with `allow_pickle=False`, JSON); a model's arrays are checked before a compiled kernel walks them (`NumpyHistGradientBoostingClassifier._validate`); a length or count read from a file or a command bounds nothing it has not been checked against (the native engine's `ipc::Reader::count`, its PCM block's size); an external program is run by its full path.
- Prefer contiguous NumPy arrays where practical; several rendering and DSP paths assume NumPy-friendly numeric buffers.
- The deck's state is the player's report: a control sends a request and shows `sig_deck_state` / `sig_playback_status`; do not set a transport state in the GUI or the player's worker (the Python engine's `PythonDeck` is that engine's player).
- Keep Qt signal semantics stable. Many slots expect notification-only signals and then read shared model state.
- A frequent report from another thread to the GUI is the newest value with one queued notification at a time (`core.player._Latest`: the playhead time, the output peak), never a queued signal per value: queued signals are not merged, so they pile up while the GUI is busy and replay stale values after. Progress from a loop is reported when its percent changes. The output buffer stats go every 0.25 s.
- A label whose text changes every frame (a time, a status line) must not ask for a layout each time: fixed in both directions (`setFixedSize`, or a fixed width and height), or a `LiveLabel` when its width follows the layout; plain text when it holds no markup (a rich-text QLabel builds a text document per change).
- If you change view registration or naming, update `views.base.REGISTRY` consumers accordingly.
- A new tool button or action gets a shortcut action: its entry in `ui.shortcuts.ACTIONS`, its handler (`shortcut_handlers` of the part that owns it), and its shipped keys in `assets/shortcuts/default_shortcuts.json` (every action has one; unique, in the tier of what it does, not a system's own: Ctrl+Alt+Del / arrows / F-keys, Ctrl+Alt+L / T (Linux lock screen, terminal), Alt+F2 / F4, Ctrl+Q / W / H (macOS quit, close, hide), Ctrl+Space, Ctrl+Esc, nor a graphics card overlay's: Alt+R / Z, Alt+F1 / F3 / F9 / F10, Ctrl+Alt+R / M, Alt+Shift+R, Shift+F12, F12).
- Every text shown to the user goes through `core.i18n.tr()`: placeholders with `.format()` (no f-string inside `tr`), a whole sentence per case rather than words spliced into one (`tr_n` for counts), `tr_mark()` for a module-level table (translate it where it is shown). Logic never reads a displayed text (combo items carry their value as data). `tr` is never a local name (a function binding it cannot call it). After changing texts run `uv run python build/translations.py` and translate the new / fuzzy entries of each catalog.
- Not translated: the main screen's DJ terms (Tempo, Volume, BPM, Key, Bars, the CUE buttons' SET / DEL / MEMORY / JUMP / CALL, the score's accel. / rit.), stored data (phrase labels, cue names, Rekordbox XML), logs, product names. Terms: JumpCUE and CUE point stay as they are (never hot cue / memory cue); the key notation 1A..12B is Alphanumeric (never Camelot); Japanese follows the rekordbox Japanese manual's terms.

## Build / Packaging
- PyInstaller spec is `build/mixlyzer.spec`.
- The spec does not bundle `config.json` (it holds personal settings); the app writes one from `default_cfg()` on first launch. Keep `default_cfg()` free of personal values.
- The spec bundles the shipped assets (`shipped()`: the `default_` models only, icons, the images shown (not the design sources `mixlyzer.psd` / `mixlyzer_large.png`), fonts, sound, style, reading tables, the language catalogs, `default_shortcuts.json`, `default_midi.json`, the native audio engine's `audioengine/native/bin` as built, with VOLK's licence), never a user's file beside them (a retrained model, `assets/shortcuts/shortcuts.json`, `assets/midi/midi.json`). `ffmpeg.exe` is not bundled (its bundling stays commented out): a package's FFmpeg goes into `_internal` by hand, where the decoder looks. `MIXLYZER_CONSOLE=1` builds a console exe (its output and errors readable) for testing.
- In a PyInstaller 6 build the bundled files are in `_internal`, which is `core.resource_paths`' root (its module path): every bundled file is read through `resource_path` (never a path from the current folder: fonts, icons, models, catalogs); a settings path (`assets/sound/click.wav`) through `setting_path`, a model's through `core.model_files.resolve_model` (as written when found from the current folder, else the bundled file). The current folder (the package folder: `app.main` makes it so) holds `config.json`, the library and the feature caches.
- There is no active `installer/` directory in this repo snapshot; do not document or depend on one unless you add it.

## Safe Assumptions
- Windows, Linux and macOS: code branches on `core.os_support`'s flags, never on `sys.platform` / `os.name` / `platform.system()` itself; a Windows API call has a fallback for the other systems.
- The library format is versioned; old docs that ignore migration are outdated.
- Root `README.md` exists, but localized docs currently live under `docs/`.
