# AGENTS (Mixlyzer)

Working notes for AI/automation agents editing the Mixlyzer codebase.

Only this file is loaded by itself. Each part's details are in an AGENTS.md beside its code: read the one of the part you change before changing it (Where the details are, below).

## Run & Environment
- Python 3.12+.
- Dependency management uses `uv`.
- Install deps with `uv sync` (with the development group: Babel, for `build/translations.py`).
- Launch the app with `uv run python -m app.main`.
- The native audio engine (`audioengine/native`) is built with `uv sync --group native` then `uv run python build/audio_engine.py` (git, Rust, and a C compiler: on Windows llvm-mingw + the `stable-x86_64-pc-windows-gnullvm` toolchain; the script's docstring has the details); its output, `audioengine/native/bin/`, is not committed. Without it the app plays on the Python engine. A running app holds `bin/`'s executable: close it before rebuilding.
- Keep root-level `config.json` available, and `deck.json` beside it (both the user's, gitignored): what each holds, their one owner (`core.settings.store`) and how they are read and written are `core/AGENTS.md`'s (The settings files).
- Keep a root-level `ffmpeg.exe` (Windows) / executable `ffmpeg` (Linux, macOS), or provide FFmpeg on `PATH` for `analyzer/audio/decoder.py`.
- Do not run the app as administrator (Windows) or root (Linux, macOS); `app/main.py` explicitly blocks it.
- Tests (`tests/README.md`; all: `uv run python -m unittest discover -s tests -p "test_*.py"`): `tests/test_*.py` the app's, each on a library or files of its own; `tests/unit/` synthetic only, by layer; `tests/library_data/` a real library read only, its reports naming no track (`MIXLYZER_LIBRARY_TESTS=1`); `tests/ground_truth/` the full analysis against a few songs' annotations in `songs.json` (keys from human sources only: a chart's Key markers timed by the song's LRC, `chart_keys.py`), and the Variants on real versions of three songs (`variants.json`, `test_variants.py`: the instrumental, the character versions, the TV size, a second purchase), the audio the runner's own, bought (`MIXLYZER_GT_TESTS=1`; tests/README.md's "Tests on real songs" names every song and why another store's copy may differ in alignment and mastering). A known bug is an `expectedFailure` test. Published tests hold no uid, local path or lyric; `tests/native_mixer/` (the mixer and the engine live on the user's tracks and devices: `verify_mix.py`, `verify_mix_real.py`, `live_deck.py`) is git-ignored.
- Windows, Linux and macOS are supported (`system.os_support`); on any other system the app warns at the start and runs on the fallbacks.

## Where the details are
- `app/AGENTS.md`: the start (App Flow), the splash and its tasks, the audio report, `AppWindow`.
- `core/AGENTS.md`: the settings files and their owner, the MIDI mapping's and the keyboard shortcuts' files, the loaded track (`DataModel`), the workflows and workers, the Analysis Flow, Segment Reanalysis, tie-ups, playback and the deck's requests and reports, External Sync.
- `core/library/AGENTS.md`: the library's one owner and its jobs, the analysis library (`core/analysis_library/`), what is stored where (Data & Persistence: library.db, the NPZ, the indexes, the thumbnails), the library's backup and its move to another device (Backup and moving: the `.mxlib` package).
- `audioengine/AGENTS.md`: the engines' shared controls, the Python engine; `audioengine/native/AGENTS.md`: the native engine (devices, WASAPI, outputs and bridges, the time stretch, the deck, the mixer, MIDI, scheduling).
- `analyzer/AGENTS.md`: the analyzer's boundary, the pipeline, beats, keys, phrases, JumpCUEs, Search by Music, Variants, Mix Candidates, Reoptimize's training.
- `ui/AGENTS.md`: the window's screen, the library widget, the editor, the settings dialog, the keyboard shortcuts' rules, `views/` (the plots, the waveform's rendering).
- `tests/README.md`: the test suites, what each needs, the songs the real-song tests use.

## Repo Map
- `app/`: Qt entrypoint and top-level window wiring (`app/AGENTS.md`).
- `system/`: the lowest layer, importing nothing of the app (the layers, `tests/test_layers.py`: system -> analyzer, audioengine -> core, third_party, migration -> views -> ui -> app; each imports only its own layer and those before it, the analyzer not even `system`: `tests/test_analyzer_boundary.py`). `resource_paths.py` the bundled files and the app's folder, `model_files.py` a learned model's file (the user's, else the shipped default), `atomic_io.py` files replaced whole, `process_worker.py` a spawned worker process's Qt lifecycle, `version.py` the app's version (pyproject.toml's: a test checks they agree).
  - `os_support.py`: the operating system, detected once per process (its first import: `app.main` at the start, each spawned worker) into flags (`OS`, `IS_WINDOWS` / `IS_LINUX` / `IS_MACOS`, `IS_SUPPORTED`), and the operations that differ by it: elevation (IsUserAnAdmin / uid 0), the taskbar identity and 1 ms timer (Windows only), hidden console windows of child programs (Windows only), revealing a file (Explorer / Finder / the folder via xdg-open), whether another program holds a key as a global hotkey (`hotkey_taken`: RegisterHotKey refused on Windows; not checked elsewhere), a background process below the others (`lower_process_priority`: below normal class / nice 10). The other Windows API users branch on the flags with their fallbacks: the window occlusion check (`ui/window_visibility.py`: user32 + DWM / Qt's exposure), the Python audio engine's scratch cursor poller (`audioengine/python/cursor_poller.py`: Win32 / the GUI's mouse events; the native engine polls the cursor itself, Windows only, else the same mouse events), the physical core count for sklearn (`analyzer/runtime.py`: Win32 / loky's own). Paths: two are compared by their `path_key` (absolute, normalized, case-folded on Windows, NFC on macOS, whose file systems take a name's NFD and NFC as one), never by `os.path.normcase` / `normpath` alone; a file whose path Windows cannot open (`path_too_long`: 260 characters or more with long paths off, `RtlAreLongPathsEnabled`) is refused by the analysis with a message before anything opens it.
  - `i18n.py`: the UI's language (Settings > View > Language, `viewconfig.language`, "" = the operating system's; applied at the next start). The languages are `assets/i18n/languages.json` (BCP 47 tags, language-REGION: `en-US`, `ko-KR`, `ja-JP` -> the language's name in itself), each one's gettext catalog `assets/i18n/languages/<tag>/mixlyzer.po`, read as it is (no compiled .mo; fuzzy entries left out). `tr()` / `tr_n()` / `tr_ctx()` translate, `tr_mark()` marks a table's texts (translated where shown); Qt's own texts (standard buttons, file dialogs) come from its `qtbase` catalogs (`install_qt`). Worker processes take the language from the environment (`MIXLYZER_LANGUAGE`). English (US) is the source.
- `core/`: the app's features, a package each (`core/__init__.py` maps them; `core/AGENTS.md`, the library `core/library/AGENTS.md`).
- `audioengine/`: the player's audio engines, the native one developed, the Python one the fallback (`audioengine/AGENTS.md`, `audioengine/native/AGENTS.md`).
- `analyzer/`: the analyzer, complete in its directory: it imports no app code (`analyzer/AGENTS.md`).
- `ui/`: Qt widgets/dialogs, a package per part; `views/`: pyqtgraph view plugins registered through `views.base.REGISTRY` (`ui/AGENTS.md`).
- The former `utils/` is spread by what each module serves: the stored forms of the marks (`cue_points`, `jump_cues`, `phrases`) in `core/analysis_library/`; what a mark is and how it is shown (`core/marks/`: `phrases.py` the labels, UNASSIGNED, the phrases ordered and the track covered, their names and colours; `jump_cues.py` the JumpCUE slots, the one check of the slot rule; `colors.py` the colour presets; it imports nothing of the library, the stored analyses or the track); what the views draw (`color`, `keystrip`, `wave`) in `views/render/`, the interface's own (`jumprender`, `semitone`) in `ui/render/`; `ui/fonts.py`, `ui/window_visibility.py`; the volume curve `audioengine/volume.py`; the key names `analyzer/music/key_names.py`. `core/search/` holds the readings (`reading.py`, with the 초성 search's keys and the names' sort keys), a title's version notes (`titles.py`: TV size, instrumental, MR, 伴奏 ...), the Variants' relations (`variants.py`), the Mix Candidates (`mixability.py`) and the Related Tracks (`related.py`), `core/tags/` a file's tags (`reader.py`, `writer.py`; `backup.py` the backup made before Write Tags writes, the tag block or the whole file in the app folder's `backups/tags/`, and putting one back), `core/library/` also `segments.py` (the index rows) and `version.py`.
- `third_party/`: export adapters such as Rekordbox XML generation and the DAW tempo map (`midi_tempo_map.py`: a Standard MIDI File of the beats, bars and keys; its docstring has the rules).
- `migration/`: read-only library-version compatibility adapter; the app never migrates by itself. No migrations between development versions: the one for libraries of earlier releases is made with the 0.2.0 release.
- `build/`: PyInstaller spec; `translations.py` updates the translation catalogs (Babel).
- `docs/`: localized docs (`README.ko.md`, `README.ja.md`).
- `assets/`: icons, fonts, sounds; `i18n/`: the UI's languages and their catalogs (`system.i18n`); `shortcuts/`: the keyboard shortcuts (`core.controls.shortcuts`).
- `library/`: user library data directory created/used at runtime. Treat as user data.
## Change Guidelines
- Keep heavy DSP, file IO, and long-running work off the GUI thread.
- The library has one owner, `core.library.service.LibraryService`: library.db, the NPZ files, the thumbnails and the indexes beside them are opened by it alone, all SQL on them is in `core/library/` and every read and write of a `{uid}.npz` in `core/analysis_library/`. Outside them, code names a job (`core.library.jobs`, `core.analysis_library.jobs`) and gets records (`core.library.records`): the GUI `read` / `write` with a ``done`` on the GUI thread, or reads the snapshot; another thread `call`; a worker process is given what it reads (a track's stored analysis included: never its path) and hands back what the owner stores. Never `sqlite3`, `LibraryDB`, `FeatureNPZStore` or another module inside them outside them (`tests/test_library_boundary.py` fails; tests aside). A new operation is a new job in the `jobs.py` of what it is about, with the SQL or file access it needs in the module inside that owns the table or file.
- Worker subprocess entry points must remain module-level pickleable callables. Do not pass Qt objects into multiprocessing workers.
- When changing config shape/defaults:
  - update dataclasses in `core/settings/config.py` (a value playing changes goes to `deckconfig`, deck.json; one the settings dialog sets to the others, config.json),
  - update `default_cfg()`,
  - keep `config.json` / `deck.json` compatibility in mind,
  - update `ui/config/` (only for a value no other place edits: every editable value has one place it is edited),
  - update any call sites assuming the old fields.
- When changing persisted analysis outputs:
  - update readers in `DataModel`/UI/views,
  - update DB segment adapters in `core.library.segments` if segment schema changes,
  - consider migration needs for existing libraries.
- `library/` is user data. Do not delete, reset, or commit its contents.
- Preserve `uid` linkage between SQLite and NPZ when editing library code.
- Analyzer speed-ups keep every output bit-identical: compare each output array of a few library tracks before and after (in fresh processes, the user's config.json), and replace a loop by a compiled one (numba, with the Python path as fallback) only where it does the same float operations in the same order (the phrase GBM's trees, the downbeat features' small medians).
- Learned models are shipped as `assets/weights/default_<name>` and the settings name the user's `<name>` (missing = the shipped one: resolved by the app through `system.model_files.resolve_model`, `core/workers/analysis_settings.py` `model_file`; the analyzer reads the file it is given); the app refuses a shipped file as a run's output before it starts (`core/workers/training_models.py` `prepare`, which also gives each request the files it reads: the model in use, `current_path`, the one it starts from, `start_path`, every model setting resolved), so Reoptimize never writes a shipped file (the phrase and JumpCUE models too), and the spec bundles the `default_` files only.
- Files the app reads may come from elsewhere (audio, models, caches, a library): never pickle (NPZ with `allow_pickle=False`, JSON); a model's arrays are checked before a compiled kernel walks them (`NumpyHistGradientBoostingClassifier._validate`); a length or count read from a file or a command bounds nothing it has not been checked against (the native engine's `ipc::Reader::count`, its PCM block's size); an external program is run by its full path.
- Prefer contiguous NumPy arrays where practical; several rendering and DSP paths assume NumPy-friendly numeric buffers.
- The deck's state is the player's report: a control sends a request and shows `sig_deck_state` / `sig_playback_status`; do not set a transport state in the GUI or the player's worker (the Python engine's `PythonDeck` is that engine's player).
- Keep Qt signal semantics stable. Many slots expect notification-only signals and then read shared model state.
- The loaded track has one owner, `DataModel` (`core.track.model`): its stored analysis, properties and marks change through its methods only (`analysis` is frozen, `properties` raises on a write, its arrays are read-only), and each change is its own signal there. A widget keeps no copy of a mark it edits (it reads the model's); a new edit is a model method or a copy set through one, never a write into `analysis`. A track change is announced by the model, not the bus.
- A frequent report from another thread to the GUI is the newest value with one queued notification at a time (`core.playback.player._Latest`: the playhead time, the output peak), never a queued signal per value: queued signals are not merged, so they pile up while the GUI is busy and replay stale values after. Progress from a loop is reported when its percent changes. The output buffer stats go every 0.25 s.
- A label whose text changes every frame (a time, a status line) must not ask for a layout each time: fixed in both directions (`setFixedSize`, or a fixed width and height), or a `LiveLabel` when its width follows the layout; plain text when it holds no markup (a rich-text QLabel builds a text document per change).
- If you change view registration or naming, update `views.base.REGISTRY` consumers accordingly.
- A new tool button or action gets a shortcut action: its entry in `ui.shortcuts.ACTIONS`, its handler (`shortcut_handlers` of the part that owns it), and its shipped keys in `assets/shortcuts/default_shortcuts.json` (every action has one; unique, in the tier of what it does, not a system's own: Ctrl+Alt+Del / arrows / F-keys, Ctrl+Alt+L / T (Linux lock screen, terminal), Alt+F2 / F4, Ctrl+Q / W / H (macOS quit, close, hide), Ctrl+Space, Ctrl+Esc, nor a graphics card overlay's: Alt+R / Z, Alt+F1 / F3 / F9 / F10, Ctrl+Alt+R / M, Alt+Shift+R, Shift+F12, F12).
- Every text shown to the user goes through `system.i18n.tr()`: placeholders with `.format()` (no f-string inside `tr`), a whole sentence per case rather than words spliced into one (`tr_n` for counts), `tr_mark()` for a module-level table (translate it where it is shown). Logic never reads a displayed text (combo items carry their value as data). `tr` is never a local name (a function binding it cannot call it). After changing texts run `uv run python build/translations.py` and translate the new / fuzzy entries of each catalog.
- The search's and the sort's Korean spellings of Japanese and other foreign words (`core.search.reading`) follow how fans write them, not the loanword rules (외래어 표기법): a rule that narrows the spellings is left out or kept beside the other spellings, as fans of anime and doujin music mostly do not follow it and a search must find every spelling they type. So か た ち are aspirated wherever they are (君 키미, 恋 코이, not 기미 / 고이) and つ is 츠 (初音 하츠네), a query's Hangul is read both as Korean and as a foreign word, the normalized keys ignore voicing (가 = 카), the 초성 search takes a plain, aspirated or tense consonant alike and つ as ㅅ or ㅈ (쓰 / 츠). A place's name keeps the loanword rule's spelling Korean knows it by (東京 도쿄, 京都 교토, 松山 마쓰야마: Sudachi's 固有名詞 地名, `reading.place_names`), a person's name the fans' (初音ミク 하츠네 미쿠). A new rule picks the spelling fans use, or keeps both.
- Not translated: the main screen's DJ terms (Tempo, Volume, BPM, Key, Bars, the CUE buttons' SET / DEL / MEMORY / JUMP / CALL, the score's accel. / rit.), stored data (phrase labels, cue names, Rekordbox XML), logs, product names. Terms: JumpCUE and CUE point stay as they are (never hot cue / memory cue); the key notation 1A..12B is Alphanumeric (never Camelot); Japanese follows the rekordbox Japanese manual's terms.

## Build / Packaging
- PyInstaller spec is `build/mixlyzer.spec`.
- The third-party notices (`assets/notices/THIRD_PARTY_NOTICES.txt`, Help > About's second tab) are made by `uv run python build/notices.py` (the Python packages `uv export` gives without the development groups, by pip-licenses, a development dependency; the native engine's crates on Windows, Linux and macOS, by `cargo metadata`; the works bundled beside them: the Python runtime, Qt / PySide6 under the LGPL with the GPL text it supplements, libsndfile, VOLK and cpu_features, the Rust standard library, llvm-mingw's runtime, FFmpeg, the fonts, Unihan, the Cantonese data the readings read). FFmpeg is the repository root's: an LGPL build (one built with `--enable-gpl` or `--enable-nonfree` is refused, here and by the spec), named by its version with its source commit, its build's recipe (BtbN's FFmpeg-Builds known by its prefix, else `FFMPEG_RECIPE`), the libraries its configuration enables and the configuration itself. Run it again when a dependency, a bundled font or data changes (`tests/test_notices.py` fails on a declared dependency it lacks). The spec ships pycantonese's HKCanCor and rime-cantonese only (its other corpora, CantoMap GPL-3.0 among them, nothing reads).
- The spec does not bundle `config.json` (it holds personal settings); the app writes one from `default_cfg()` on first launch. Keep `default_cfg()` free of personal values.
- The spec bundles the shipped assets (`shipped()`: the `default_` models only, icons, the images shown (not the design sources `mixlyzer.psd` / `mixlyzer_large.png`), fonts, sound, style, reading tables, the language catalogs, `default_shortcuts.json`, `default_midi.json`, `default_artist_names.tsv`, the native audio engine's `audioengine/native/bin` as built, with VOLK's licence), never a user's file beside them (a retrained model, `assets/shortcuts/shortcuts.json`, `assets/midi/midi.json`, `assets/artists/artist_names.tsv`). The repository root's `ffmpeg.exe` / `ffmpeg` is bundled into `_internal`, where the decoder looks, after the spec checks it with `build/notices.py` (`ffmpeg_build`): an LGPL build, the one the notices name (else the build stops: run `build/notices.py` again); without one the package leaves FFmpeg out (the decoder then takes the one on PATH). `MIXLYZER_CONSOLE=1` builds a console exe (its output and errors readable) for testing.
- In a PyInstaller 6 build the bundled files are in `_internal`, which is `system.resource_paths`' root (its module path): every bundled file is read through `resource_path` (never a path from the current folder: fonts, icons, models, catalogs); a settings path (`assets/sound/click.wav`) through `setting_path`, a model's through `system.model_files.resolve_model` (as written when found from the current folder, else the bundled file). The current folder (the package folder: `app.main` makes it so) holds `config.json`, the library and the feature caches.
- There is no active `installer/` directory in this repo snapshot; do not document or depend on one unless you add it.

## Safe Assumptions
- Windows, Linux and macOS: code branches on `system.os_support`'s flags (the analyzer on `analyzer.runtime`'s, its own), never on `sys.platform` / `os.name` / `platform.system()` itself; a Windows API call has a fallback for the other systems.
- The library format is versioned; old docs that ignore migration are outdated.
- Root `README.md` exists, but localized docs currently live under `docs/`.
