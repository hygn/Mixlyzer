# AGENTS (Mixlyzer)

Working notes for AI/automation agents editing the Mixlyzer codebase.

## Run & Environment
- Python 3.12+.
- Dependency management uses `uv`.
- Install deps with `uv sync` (with the development group: Babel, for `build/translations.py`).
- Launch the app with `uv run python -m app.main`.
- The native audio engine (`audioengine/native`) is built with `uv sync --group native` then `uv run python build/audio_engine.py` (git, Rust, and a C compiler: on Windows llvm-mingw + the `stable-x86_64-pc-windows-gnullvm` toolchain; the script's docstring has the details); its output, `audioengine/native/bin/`, is not committed. Without it the app plays on the Python engine. A running app holds `bin/`'s executable: close it before rebuilding.
- Keep root-level `config.json` available, and `deck.json` beside it (both the user's, gitignored). `config.json` holds the settings that seldom change (the settings dialog's); `deck.json` what playing changes (`config.deckconfig`: the time stretch's MT, the metronome, the TRIM, the tempo range, the MIDI input on / off, the toolbar's switches and levels, the effects picked, Search by Music's microphone; the deck's momentary state, FX ON, the EQ / COLOR knobs, CUE, the crossfader, a tapped BPM, is not kept), written a second after it changes (`AppWindow._deck_save`, `config.save_deck`; `save_cfg` the other). Where `deck.json` is missing, its values are taken from `config.json`'s playbackconfig once. `load_cfg()` reads both and rewrites one only where it is not what it reads as (missing, a key added or migrated: GUI and worker processes call it to read at once, and Windows refuses to replace a file another process holds; `utils/atomic_io` also tries a replace again for half a second); one it cannot read (not JSON, not UTF-8, not an object) is moved aside as `<name>.unreadable-<time>` before its defaults are written, and the start says so (`config.unreadable_settings()`). Every editable value has one place it is edited: the settings dialog shows none of the main screen's (the MT button, the TRIM knob, the metronome's on / off, the toolbar's).
- Keep a root-level `ffmpeg.exe` (Windows) / executable `ffmpeg` (Linux, macOS), or provide FFmpeg on `PATH` for `analyzer/audio/decoder.py`.
- Do not run the app as administrator (Windows) or root (Linux, macOS); `app/main.py` explicitly blocks it.
- Windows, Linux and macOS are supported (`foundation.os_support`); on any other system the app warns at the start and runs on the fallbacks.

## Repo Map
- `app/`: Qt entrypoint and top-level window wiring.
  - `main.py`: app bootstrap (the UI language first, before the UI is imported), dark palette, font loading, library-version migration flow. Kept light: a spawned worker process imports the main module again, so `app.window` is imported by the startup, not at the top.
  - `startup.py`: the startup splash (the task, what it is doing, a Task and an Overall progress bar, and under them the console's last lines: `startup_console.py`, `ConsoleLines` tapping sys.stdout / stderr from `main()`'s start (the print hook, installed later, writes through it; taken out when the splash closes), drawn as a terminal's: the time since the start, a coloured tag per source (`[Startup]`, `[AudioEngine]`, ...), a finished task's time right-aligned, a failure in the danger colour; the engine's lines, printed on its relay thread, drawn at the next repaint) and the slow work done before the window opens, in order: the heavy imports, the Python audio engine's numba kernels (JIT, from numba's disk cache; skipped when the native engine is built), FFmpeg's first run, the search readers (`reading.warm_up`), every stored reading's search keys (`reading.keys`' LRU cache), then `AppWindow(progress=)`. numpy's and scipy's OpenBLAS load with one thread in this process (`one_blas_thread()`, first in `main()`: the GUI does no heavy linear algebra, and each OpenBLAS sets aside buffers per thread, about 1 GB committed on 16), the variable taken back once they have, so the spawned worker processes keep a thread per core. Each task's weight is its measured time; events are taken between updates except while the window is built (only the splash repainted there, so no timer reaches a half-built window).
  - `audio_report.py`: the audio setup printed at the start (`[AudioEngine]` lines: the engine that plays and why, the master's device / API / mode / buffer, the headphones' and the booth's outputs, the process's priority, the mixer's switches, MIDI); what the engine then opened follows as its own lines.
  - `window.py`: `AppWindow`, workflow wiring, EventBus wiring, External Sync, metronome, model updates.
- `core/`: shared runtime/state/integration layer.
  - `config.py`: dataclass config schema, defaults, `load_cfg()` (`outputconfig`: the headphones' / booth's output).
  - `os_support.py`: the operating system, detected once per process (its first import: `app.main` at the start, each spawned worker) into flags (`OS`, `IS_WINDOWS` / `IS_LINUX` / `IS_MACOS`, `IS_SUPPORTED`), and the operations that differ by it: elevation (IsUserAnAdmin / uid 0), the taskbar identity and 1 ms timer (Windows only), hidden console windows of child programs (Windows only), revealing a file (Explorer / Finder / the folder via xdg-open), whether another program holds a key as a global hotkey (`hotkey_taken`: RegisterHotKey refused on Windows; not checked elsewhere), a background process below the others (`lower_process_priority`: below normal class / nice 10). The other Windows API users branch on the flags with their fallbacks: the window occlusion check (`utils/window_visibility.py`: user32 + DWM / Qt's exposure), the Python audio engine's scratch cursor poller (`audioengine/python/cursor_poller.py`: Win32 / the GUI's mouse events; the native engine polls the cursor itself, Windows only, else the same mouse events), the physical core count for sklearn (`analyzer/runtime.py`: Win32 / loky's own).
  - `i18n.py`: the UI's language (Settings > View > Language, `viewconfig.language`, "" = the operating system's; applied at the next start). The languages are `assets/i18n/languages.json` (BCP 47 tags, language-REGION: `en-US`, `ko-KR`, `ja-JP` -> the language's name in itself), each one's gettext catalog `assets/i18n/languages/<tag>/mixlyzer.po`, read as it is (no compiled .mo; fuzzy entries left out). `tr()` / `tr_n()` / `tr_ctx()` translate, `tr_mark()` marks a table's texts (translated where shown); Qt's own texts (standard buttons, file dialogs) come from its `qtbase` catalogs (`install_qt`). Worker processes take the language from the environment (`MIXLYZER_LANGUAGE`). English (US) is the source.
  - `midi.py`: a MIDI controller's mapping, the shortcuts' file convention: the shipped `assets/midi/default_midi.json` (empty) and the user's `assets/midi/midi.json` (gitignored), action id -> messages as rekordbox's CSV writes them ("900B" a note, "B000" a CC, "E000" a pitch bend), options after: H a 14-bit CC (LSB at data 1 + 32), I inverted, a relative encoding O (offset 64) / T (two's complement) / S (sign-magnitude; none: guessed per value), + / - only that direction of a relative control (`Message`). The actions (`ACTIONS`) are a DJ controller's, not the keyboard shortcuts': per deck (`deck{n}.`, up to `DECKS` = 8) PLAY / PAUSE, CUE, track start, tempo slider / range / reset, pitch bend, the jog's mode (JOG MODE VINYL / CDJ, lit in VINYL), touch / top / side / SHIFT search, CUE CALL, JumpCUE pads and their delete, beat jump; per mixer channel (`mixer.ch{n}.`) the fader, EQ HI / MID / LOW, trim, COLOR (its Sound Color FX knob), CUE and the level meter; the headphones' mix and level (the crossfader's act has none: not shown to the user); the browser (BROWSE knob turned / pressed, BACK, zoom), LOAD, MASTER TEMPO, MEMORY / DELETE; the effects (`fx.`, the Effects group: each Sound Color FX's button and PARAMETER; Beat FX's engine acts are left out: not shown to the user; with their lamps). Each has a kind (button, fader, knob, touch, meter): the engine's code (`code`, the deck's index in bits 24+) or the GUI's actions (`gui`: a knob's per direction), its lamp. Settings shows the `shown` ones only: deck 1, and of the mixer channel 1's fader, EQ and level meter; the others (decks 2-8, trim, channel CUE, headphones) are handled by the engine but kept hidden (their mapping is kept on save). The GUI's actions go to the engine as `ACT_GUI` + their place (passed back, run as their shortcuts by `AppWindow._on_midi_events`; a knob's steps repeated). `import_rekordbox_csv` reads rekordbox's MIDI CSV: deck 1's column (a whole message or a channel offset to the input column), mixer channel 1, the global browser / headphones rows (the crossfader's left out) and ChannelLevel's output, the CFX knobs (`CFXParameterCH1` / `CH2`: the channels' COLOR); FX1 (Beat FX) is left out; other decks are left out.
  - `shortcuts.py`: the keyboard shortcuts' files: the shipped `assets/shortcuts/default_shortcuts.json` (only read; `save` refuses it) and the user's `assets/shortcuts/shortcuts.json` (gitignored; only the actions changed from the shipped keys, a missing file = the shipped keys), both action id -> key sequences in Qt's portable text.
  - `track/`: the deck's loaded track, its one owner (`core/track/__init__.py` maps it). `model.py`: `DataModel`, what the track is (its stored features, properties, album art, decoded audio) and its marks as edited (beats and tempo rows, keys, phrases covering the track, JumpCUE pairs, CUE points; `beats`, `tempo_segments`, ...) with the undo history and the unsaved flag. Everything that changes them goes through its methods (`load`, `set_beatgrid`, `set_key_segments`, `set_phrases`, `set_jump_cues`, `set_cue_points`, `set_automatic` for a reanalysis's automatic result, `undo` / `redo`, `mark_saved`, `set_decoded_duration`, `set_album_art`, `set_predecoded_audio`), each telling its own signal at once (`sig_loaded`, `sig_properties_changed`, `sig_album_art_changed`, `sig_audio_changed`, `sig_beatgrid_changed`, `sig_keys_changed`, `sig_phrases_changed`, `sig_jump_cues_changed`, `sig_cue_points_changed`, `sig_edits_changed`); `features` / `properties` are read-only dicts (a write raises; the marks' stored forms follow each edit there) and the marks' arrays read-only (an editor copies, changes, sets). `stored_edits()` the blocks the editor saves. `marks.py` the editor's forms made from the stored features and written back (pure functions); `history.py` the snapshots.
  - `event_bus.py`: Qt signal hub for the app's requests and reports (the deck, the library, the workers, the settings); the loaded track's changes are the model's signals, not the bus's.
  - `workers/`: analysis, segment reanalysis, optimizer, and Rekordbox worker implementations.
  - `workflows/`: Qt-facing worker lifecycle and queue orchestration.
  - `library/`: the library (library.db, the thumbnails, music_search.db, variants.db; the tracks' stored analyses are `analysis_library/`'s, below, kept by the same owner), its one owner and every operation on it, behind one boundary (`core/library/__init__.py` maps it; `tests/test_library_boundary.py` holds it: outside `core/library/` and `core/analysis_library/` no `sqlite3` but `core/tieup_web.py`'s own web cache, no import of the modules inside but a type under `TYPE_CHECKING`, no path of a track's `{uid}.npz`, `analysis_path`). Outside code uses three modules:
    - `service.py`: `LibraryService`, the owner (made by the startup, `app.startup`, handed to `AppWindow`): a thread of its own with the one connection to library.db and the others' files; the jobs run there in the order asked (a read asked after a write sees it). The GUI asks `read(job, *args, done=, failed=)` / `write(...)` (``done`` on the GUI thread, a deleted widget's callback skipped; after writes the snapshot is read again before their ``done``); another thread of the app asks and waits, `call(job, *args, write=)` (the tie-up web lookup, the Export tab's tag writer, the Rekordbox XML sync, Search by Music's index loading; refused on the GUI thread, which would freeze, and from a job, which would wait for itself). `LibrarySnapshot` (the tracks, their readings and tie-ups, the playlists and their entries, the Variants' relations; ~35 ms at 400 tracks) is sent with `updated` and `EventBus.sig_lib_updated`: the GUI reads it at once (`find_file`, `track`, `playlist_tracks`; External Sync's questions).
    - `jobs.py`: every operation on the library, one function each, `job(lib, *args)` with `Library` (`db`, `path`, `features`), grouped by what they serve (tracks, readings, playlists, the structured searches, tie-ups, the indexes, thumbnails, an analysis stored, tracks removed: the last two write the stored analyses too). A new operation is a new job here; its callers name it (`library.write(jobs.save_tieup, uid, t, old, versions, done=...)`), never SQL.
    - `records.py`: what jobs take and give (`TrackRow`, `PlaylistRow`, `IndexTrack`, the segment rows, `field_readings`, `canonical_uuid4`).
    - Inside, used by the jobs alone: `db.py` (`LibraryDB`: the tracks, readings, tag sources, playlists, segment tables, the transition search), `tieups.py` (the tie-up tables and their SQL; the domain is `core/tieup.py`), `thumbnails.py`, `music_index.py` (music_search.db; `LandmarkIndex`, the read-only connection the owner lends Search by Music's searches: on its thread they would hold the other jobs), `variants.py` (variants.db).
    - Worker processes compute only and never open the library: they are given what they read and hand back what the owner stores (the analysis: `store` in its last item, `jobs.store_analysis`; Re-read Library: `jobs.reading_texts` in, `jobs.apply_readings` / `apply_work_readings` out; Index Now: `jobs.index_plan` in, `jobs.store_music_entry` / `fingerprint` out; Reoptimize: `analysis_jobs.training_tracks` and their stored analyses' annotations, `training_features`, 50 tracks a job so the GUI's jobs run between, in; `optimizer.library_tracks` holding them in the process).
  - `analysis_library/`: the analysis library, each library track's stored analysis `{libpath}/{uid}.npz` (`core/analysis_library/__init__.py` maps it), kept by the library's owner (one thread for all the library's files: an analysis stored or a track removed writes library.db and the NPZ in one job). `jobs.py` (imported as `analysis_jobs`): every operation on the stored analyses, `job(lib, *args)` as the library's (`features`, `features_stamp`, the editor's `save_edits` with its `EDIT_BLOCKS`, Reoptimize's `training_tracks` / `training_features` with `TRAINING_KEYS`); inside, used by the jobs and the owner alone: `store.py` (`FeatureNPZStore`, the file format: flattened keys, NumPy values only, written atomically; `load_keys` decompresses only the keys asked for).
  - `music_search/`: Search by Music, the library found by a hummed / sung / whistled melody or by the song itself played from a phone or a speaker, through the microphone (or a file); no mode is picked (`search.search_audio`): a voice's pitch by YIN for all frames at once first (`query.py`, ~0.1 s; a whistle told by its nearly pure tone above 950 Hz and tracked in its own range; a single voice or instrument: `VOICE_LIKE` of its frames with a clear period); then spectral-peak landmarks, tens of ms, for a recording of the song itself (`landmarks.py`, Wang 2003: peak pairs hashed, the song whose hashes line up at one offset, voted in NumPy on the index's rows of the query's hashes; a mix's query keeps three times the index's peaks, `QUERY_PEAKS_PER_SEC` / `QUERY_FAN_OUT`, so a crowd's calls and screams, which take a second's strongest peaks, leave the song's, at least `MIN_VOTES`; a single voice is searched at the index's density, at least `VOICE_MIN_VOTES`; then nothing else is searched); else at once on three threads: for a mix, the landmarks through a DJ's tempo with the key locked (`landmarks.search_tempo`: the query's peak times scaled to the song's by each of `TEMPO_FACTORS`, +-8 % in 1 % steps, paired again and voted at once; at least `MIN_TEMPO_VOTES`; measured on a DJ set's room microphone against its master: the right song first 0.44 -> 0.72 joined over time, ~300 ms a search), the voice's pitch (every `QUERY_HOP`, 23 ms), and, for a mix, the melody extractor's line of the query (read as the references are) within +-1 semitone (a recording played at another tempo or pitch; kept only under `MUSIC_MAX_COST`, a quarter semitone a frame: the extractor finds lines in noise too), the two melody searches' songs joined by their lower cost; the voice and the extractor's line against two reference lines a song (`melody.py`: the predominant melody of the stereo centre, where a lead vocal is mixed (the mix's spectrum weighted by how alike left and right are, its harmonic part by the mix's HPSS mask in the same STFT: `harmonic_parts`, no HPSS of its own), and the mix's top line, the highest of its 3 strongest contours: an instrumental intro's riff; both from `analyzer.beat.melody_contour` (its CQT salience: a salience from the STFT itself, as MELODIA's, took half the time but found 3 - 4 points fewer songs over 416 queries); in the analysis the mix's contours are the ones its frame features found in the same harmonic part, handed over by `melody_contour.take_contours`, so they are not found twice; at 0.4 / 0.2 / 0.1 s frames, u8 in thirds of a semitone) by a subsequence DTW cascade over all songs (`matcher.py`: tempo x0.5-2, the octave folded, a transposition lane per third of a semitone within +-3 semitones, all lanes as SIMD, the kernels without the GIL on `SEARCH_THREADS` threads (a quarter of the cores, 4 at most: never all of them beside the GUI); `SEARCH_STAGES`: whole semitones over all songs at 0.4 s, every third at 0.2 s, the thirds around the key at 0.1 s; about 0.5 s at 10,000 songs); the microphone's window under -55 dBFS is not searched. The index is `{libpath}/music_search.db` (`core.library.music_index`, below). The research behind it (synthetic queries, what failed) is in `benchmark/qbh_research` (not committed).
  - `variants/`: the library's Variants, its tracks that are versions of one song (the same audio: another encode, copy or rate; another vocal; the instrumental / off vocal; an edit, a TV size; not arrangements, remixes or bootlegs: another song's form), found from the analysis's stored features alone, no audio (`fingerprint.py`: frames on the beat grid, subdivided so the frame rate sits in 200 - 400 a minute (a grid read at half or double tempo gives the same frames; a query near the octave's edge also tries the neighbouring one), per frame Philips-style bits of the overview's 12 bands, 11 over the mix + 5 over the backing bands (20 - 200 Hz, 6.3 - 20 kHz), their reliability, and the vocal range's level; index rows the backing bits of 6 frames at every 8th frame, a query every frame with its 6 weakest bits flipped, votes per (track, offset), the candidates verified on the stored codes: 32-frame stretches whose reliable backing bits agree >= 0.92, related when the mix's bits agree >= 0.8 on them and the shorter track is half covered; the same mix at >= 0.98, an instrumental by its vocal range 2 dB lower on a quarter of the frames, an edit by the covers differing by 0.2; ~20 ms a track with its query; measured on 1353 tracks queried against each other: 450 relations, no different song called a version); `relations.py` the relations' groups; its index is `core.library.variants` (below). The research behind it is `benchmark/fingerprint_research` (not committed).
  - `tieup.py`: tie-ups, their domain (`Work`, `TieUp`, the categories, roles and languages, names' keys and readings, the comment's suffix; their tables and SQL are `core.library.tieups`', each function named here run through the owner's jobs): the works a track is used in, owned by the track as everything else is (the library shows its rows: no song entity, nothing shared behind the scenes). A work (the IP a song comes from: what matters, its role a bonus): anime, game, drama, movie, media mix, 2D idol, commercial, other; its names after AniDB's title types and MusicBrainz's aliases: official titles, each language's first its primary (the library and the comment show the title in the UI's language and region, else in its language, else the first), and names never shown (synonym, short, search hint), all read by `core.reading` so a work is found in any script; every name's language an `ll-RR` tag (ISO 639-1 + ISO 3166-1 alpha-2: `ko-KR`, `ja-JP`, `en-US`; a romanization is a synonym under the original language; `is_lang`, the table's CHECK); its web references. A tie-up: the track, the work, the role (not specified: the work alone, shown as its title; opening, ending, insert, theme, character / unit / image song, title / login screen, main screen, event, BGM, other), a number (OP2) and a detail (episodes, the song's version); one per (track, work, role, number). Tagged automatically only where the user acts: a new track's first analysis takes its versions' tie-ups (`core.library.tieups.match_new_track`, in `jobs.store_analysis`: its Variants group's, each once; never a reanalysis or Index Now), and a tie-up added in the Tie-ups tab goes to the track's versions where they lack it when `libconfig.tieup_to_versions` says so (Settings > Library, on by default; `save_tieup`'s versions; edits and removals stay on the track). A work found again (a web lookup's) is the library's row it is (`find_work`: the same Wikidata item or Wikipedia page among its references, else an official title or synonym in common, compared by `name_key`: NFKC, case folded, letters and digits in their own script, no reading, so two Han spellings read alike stay two works; abbreviations and search hints never; two works matching: a new one, left to the user to merge); `add_names` adds names and references, never overwrites, the category kept. A web tie-up adds no "not specified" where the track has the work, and a role found replaces the work's "not specified" in its place (`core.library.tieups.add_found`). A server for shared tie-ups is left for later: nothing here is made for one (the ids are the library's own UUIDv4s).
  - `tieup_web.py`: tie-ups looked up on Wikimedia (`libconfig.tieup_web_search`, off by default: it sends a track's title and artist; and the Tie-ups tab's Find on the Web): looked up by several names and searches (`queries`: the title, without a "feat. …" or a version note at its end ("(TV size)", "(Club remix)", "(ふたりば～じょん)"), without a subtitle after 〜 / ~; the artists the artist field and the title credit, "A from B" / "A feat. B" split, a character's credit "Unit[キャラA(CV.声優A)&…]" giving the unit, the voice actors, the characters); the song's own Japanese Wikipedia page first (`曲名`, `曲名 (曲)`, `曲名 (シングル)`, `曲名 (歌手の曲)`; read whole), else the searches in turn (each name quoted, with each artist, the album's name), each one's first pages read where they name an artist (its letters or sounds), until two pages agree on a work or 8 are read; the song found in a page's lines as the library's search finds a title (`found_in`: `reading.find`, one sound off per 5 letters), each with the lines describing it (`_entry`: a table row's cells, a list item's or a label's deeper lines, a heading's paragraph); a tie-up read as Japanese articles write it (`mentions`: (medium)「work」 … role(number), and on the song's own page a work named by its medium alone, with no role (メディアミックスプロジェクト『作品』にて誕生); a work inside the work (作中作『…』) not one; or a work's page, or its discography page (`listed_work`: 作品のディスコグラフィ), listing the song: that work, under the role before the song, in its description or in the heading / label above, else not specified; a page read as a work only where it is one by its Wikipedia categories); a work's page by its categories (`page_category`: the works' indexes `アニメ作品 あ` / `漫画作品 ゆ`, a year's `2019年のコンピュータゲーム`, a company's `…のアニメ作品`, `…ゲームソフト`, or its franchise's own category on a page no person's, group's or record's; a 2D idol where it or its categories' categories are `アイドルを題材とした…`, or a fictional idol group, `架空の音楽グループ` with idols in its name or categories; a fictional band without idols is its work's); the category a 2D idol, else the medium, else the work's Wikidata class, else its page's categories; an episode range in the same sentence its detail; a work is its page (the names linking one page are one work); the work's names in other languages from its Wikidata item's labels and aliases (codes mapped to `ll-RR`, others left out), its pages as references. Sure (written without asking: `tag_track`; the one Find on the Web checks: both alike), decided by the work, of the works whose pages are works': on the song's own page, the work it names most, with its first role by OP, ED, theme, insert, ...; from the searches, the work most pages name, with the role more of them name than any other, else not specified (ties: the category by anime, game, 2D idol, ..., then the one found first; whatever was found gives a tag: a little wrong now and then is better than none). The others are suggestions only. The answers' cache key carries `RULES` (raise it when the reading or the pick changes). One request at a time, a second apart, Wikimedia's User-Agent and maxlag (`shared()`); answers kept 30 days in `cache/tieup_web.db` (gitignored). `core/workflows/tieup_web.py` runs them off the GUI thread (a new track the analysis's versions gave none, `features_properties["new_track"]` / `["tieups"]`; each a task of the Workers window's Tie-up Lookup tab: `queued` / `started` / `done`, made tasks by `AppWindow`).
  - `external_sync.py`: External Sync (another program's deck followed, received as OSC) / transport lockout; `osc.py` the strict OSC 1.0 decoder it reads with.
  - `player.py`, `timeline.py`, `taskmanager.py`: playback, viewport timeline, worker/task UI state. The deck (the native engine's `src/deck.rs`, or `audioengine/python/deck.py` on the Python engine) takes requests (`EventBus.sig_deck_action`: `client.ACT_*` codes pressed / let go; `sig_tempo_requested`, `sig_tempo_range_requested`, `sig_volume_requested`, `sig_jump_to_requested`, `sig_call_requested`, `sig_deck_marks`) and reports what it is (`DeckReport` through `sig_deck_state`, `sig_playback_status`, `sig_tempo_factor_changed`): the GUI shows the report only, never a transport state it computed (playing, tempo, tempo range, volume, the cue point, the PLAY / CUE lamps, the armed JumpCUE). The native feeder's report waits for every command sent to be taken (`cmd_done`), so a request on its way is not shown undone. `PlayerController` starts the audio engine of Settings > Audio's Audio engine (`playbackconfig.audio_engine`, applied at the next start: "native", the default, falls back to the Python engine where the native one is not built or cannot start; "python" never starts the native one; `player.native` says which plays) and its audio-thread worker drives the engine's feeder (`NativeFeeder` or `PCMFeeder`). Each engine has its own buffer setting (`native_buffer_ms`, default 20; `python_buffer_ms`, default 80): the dialog shows the playing engine's with the rest and the other's under Advanced (`set_audio_engine`). The output device (`output_device`, by the name the playing engine lists: `player.output_devices()`; "" the system's default) changes while playing (a device is found by its name, or the only one of that name but its Windows instance number, "Speakers (2- DDJ-400)" plugged in again as "(3- DDJ-400)": `device::pick`; one not there: the master plays on the system's default meanwhile, a bus on a device of its own (headphones, booth) waits for its device, tried each second, never taking another: `device::NOT_PRESENT`, so a CUE never reaches the speakers and an exclusive stream never locks the master out; a failure said once until it changes, an audio client's code in words: `device::explain`), at the session's format (converted by the system); on the native engine the master goes to a channel pair of it, the headphones and the booth to channel pairs of it or to devices of their own (`set_routing`, below). A scrub's positions reach the engine at most every `SCRUB_INTERVAL_MS` (30 ms, the newest; the views follow the drag itself); the decoded PCM goes to the native engine in a shared block (`client.share_pcm`, `NativeFeeder.adopt` in the decode thread), which is also `DataModel.predecoded_pcm` (no copy).
- `audioengine/`: the player's audio engines. The native one is developed; the Python one is the fallback, kept as it is (its renderer design, `PCMFeeder`'s docs, is what the native one ported): deck 1 on one output, no MIDI, no mixer, no headphones or booth. Audio work goes to the native engine; the Python engine gets only what keeps deck 1 playing as the app expects.

## Analysis Flow
- A load onto the deck (a drop on the deck, the library's load: `sig_request_load_track`, External Sync) goes to `AppWindow.load_track`: the file plays at once (decoded; a new file shows its tags meanwhile and the decoded length) and `AnalysisWorkflow.analyze(path, listener=)` gives the deck its features (a library track's stored ones at once, a new file's when analyzed: the analysis's results alone are applied then, `DataModel.load(keep_audio=True)`, the playback goes on; applied only while the deck still holds that file). A file only analyzed into the library (dropped on the library, a playlist's new files, Reanalyze on files not analyzed yet) goes by `sig_request_analyze` (no listener; a library track's is not analyzed again).
- Full-track analysis runs in a spawned subprocess via `core.workers.analysis.AnalysisWorker`. The process runs with one BLAS thread (`threadpool_limits` in `core/workers/analysis.py`): the analysis runs its own threads, and BLAS threads on top only competed (the outputs are the same; a track about 20 % faster, a third less CPU).
- The worker calls `analyze_for_library` (`core/workers/analysis.py`): the file's tags read (`core/audio/track_tags.py`), `analyzer.pipeline.track.analyze_track` run, its `TrackAnalysis` made into what the library stores.
- The pipeline (`analyzer/pipeline/track.py`):
  - decode/load audio,
  - HPSS split (always on, not a setting; its median filters are a sliding median kept sorted, `analyzer/audio/running_median.py`, equal to scipy's `median_filter` and several times faster),
  - overview waveform (its own 48 kHz decode: min / max of 32768 columns, the power of 12 log-spaced bands in 8192 columns, and the detail waveform's three-band scale),
  - beat tracking (`analyzer.beat.general.track` on the frame features; frames on the fixed grid `frame_features.FRAME_HOP_LENGTH` (256); the models were trained on 22050 Hz HPSS frames; every analysis runs at 22050 Hz (`analyzer.settings.ANALYSIS_SAMPLE_RATE`, not a setting) with HPSS, so the tracker reads the analysis's own frames): per training seed, tempo candidates from the activation's periodicity -> section decoding into steady (tempo, phase) grids with one section cost -> exact tempo / phase fit -> sudden vs gradual tempo changes (linear ramps, continuous or with a jump at one end) -> bar-supported half-beat phase (bars of 2, 3 or 4 beats) -> metronome critic (3:2 / 4:3 misreads) -> tempo-change boundaries on the refine onset -> slow tail held -> drifting sections -> tiny re-syncs merged -> junction rules (no too-close / too-far beats at grid changes) -> bars (a Viterbi over 3- and 4-beat bars on two downbeat observers; an odd bar costs, a new section starts free); then the seed whose grid agrees most with the other two. Every tempo is read in the octave from BPM min. The rows have `inizio` on a downbeat and `ts` the bar length (`bars.to_rows` splits a row where the bar length changes), so the segments always rebuild the beats and downbeats,
  - JumpCUE detection,
  - key analysis (`analyzer.key.chord_key.analyze_keys` on the beats, the downbeats and the phrase starts; no keys when it fails),
  - Search by Music's index (`core.music_search.indexing.index_audio`, handed to the pipeline as `index_music`, on the decoded stereo, the HPSS's harmonic part and mask and the frame features' melody contours already made, about 2.2 s of CPU a 4-minute track; Index Now, decoding and making its own HPSS mask, about 3 s; `searchconfig.music_index`, on by default; written to `music_search.db` once the track has its uid; a failure leaves the track unindexed, never the analysis undone),
  - the results handed back (the process never opens the library: its result carries ``store``, the segment rows, the music entry and the cover's bytes) and stored by the library's owner (`core.library.jobs.store_analysis`, a write job: `AnalysisWorkflow._on_success`): the track's row (a reanalysis keeps the user's metadata, the row read then; a new track given its uid), tag sources, segment tables, NPZ (`FeatureNPZStore`), thumbnail, Search by Music's entry,
  - the Variants' fingerprint (`core.library.variants.put` on the features, always on: stored, then queried against the library's; a failure leaves the track out of the Variants, never the analysis undone), then, for a new track only (not in the library before this analysis), its versions' tie-ups (`core.library.tieups.match_new_track`), in the same job; the GUI looks a new track left without on the web when Settings > Library says so (`core.workflows.tieup_web`).
- A library track's stored features are read by the library's owner (`AnalysisWorkflow._start`), no process started.
- Reanalyze-track requests (`sig_reanalyze_requested`: the path and analysis settings for this run only, or None) force a fresh full analysis and overwrite stored results.

## Segment Reanalysis
- Partial reanalysis is orchestrated by `core.workflows.segment_reanalysis.SegmentReanalysisWorkflow`.
- Work is offloaded to a subprocess via `SegmentReanalysisWorker`.
- Supported modes currently include:
  - beat segment reanalysis,
  - static key selection reanalysis (`chord_key`: the key with the most evidence over the selection),
  - dynamic full key reanalysis (`chord_key` on the editor's current beatgrid, bars and phrases),
  - JumpCUE reanalysis (with AutoCUE on JumpCUEs, the AutoCUE JumpCUE goes where the editor's current phrases' lead-in ends; with AutoCUE on CUE points, the Phrase page's CUE button places it),
  - phrase reanalysis (the whole track on the current beatgrid; the CUE points stay).
- Results go to the loaded track as edits, with or without the editor shown (`DataModel.set_beatgrid` / `set_key_segments` / `set_phrases(normalize=True)` / `set_jump_cues`, and `set_automatic` for a whole-track reanalysis's automatic result): undoable, saved with the editor's next save; they are not a separate analysis system.

## Data & Persistence
- Track metadata lives in `library/library.db` in the `tracks` table, keyed by `uid` (PRIMARY KEY, canonical UUIDv4).
- `track_readings` (uid, field, slot) holds the romanized readings of each track's title / artist / album (`core.reading`): the search's intermediate representation, up to 7 a field, each with its source (ja, zh, yue, ko-hanja, vi, zh-tw, ko, text, or user). The readings the user added (the track panel's Search Index tab: only the cells typed there; source `user`) are kept and come first; the automatic ones after them are made anew in the stored languages whenever the track is written (`LibraryDB.upsert` -> `refresh_readings`, `core.library.db.field_readings`), so a language unchecked removes only automatic readings. An automatic reading the user removed (emptied, Delete, or typed over in the grid) is kept in `track_reading_removals` (uid, field, reading) and left out from then on, whatever the languages; typed again, it is the user's. Settings > Search's Re-read Library (also started when what the stored readings depend on changes: `searchconfig.stored_readings()`) reads every track again: the library's owner gives a spawned process every text (titles, artists, albums, the tie-up works' names), the process reads them (`core/workers/reading_refresh.py`: the readers are Python, the GUI's interpreter lock spared) and the owner writes the readings back, 50 tracks a job (`core/workflows/reading_refresh.py`). The library's text search matches Title / Artist / Album by these too.
- Playlists (`playlists`, keyed by their own UUIDv4 `uid`) hold one `playlist_tracks` row per entry, (`playlist_uid`, `position`) -> `track_uid`: a track may be in a playlist more than once, so the UI addresses an entry by its position (reorder / remove), never by the track. Removing a track removes its entries and closes the playlists up.
- BPM and key transitions are also persisted in:
  - `track_bpm_segments`
  - `track_key_segments`
- Tempo segments are rows `[start, end, bpm, inizio, ts_num, bpm_end]` (`analyzer.music.tempo_rows`). A `bpm_end` that differs from `bpm` is a linear tempo ramp (tempo linear in time from `start` to `end`; its beats come from the closed-form phase); rows without it (5 columns, older data) or with it equal are steady. `inizio` is a downbeat on the row's own grid. `track_bpm_segments.bpm_end` mirrors it (NULL = steady): transition search reads a ramp as a change from its start to its end tempo, and a phrase section inside a ramp gets the tempo at its midpoint. The editor keeps ramp rows (cut / merge / shift follow the tempo line; Assign makes the row steady at the reference BPM; the ramp start / end buttons make the reference BPM the row's start or end tempo, its first beat kept), and the Rekordbox export (which has no ramps) writes a ramp as steps of steady tempo, one TEMPO entry each: a step per beat, or several beats while every beat stays within Settings > Library's Tempo ramp tolerance (`libconfig.rekordbox_ramp_tolerance_ms`, default 1 ms), measured as written (Inizio in ms, the BPM rounded down to 0.01 so a step never puts a beat just before the next one's).
- Numeric feature arrays live in `{libpath}/{uid}.npz` (the analysis library: `core.analysis_library`, its `store.FeatureNPZStore`, read and written through `analysis_jobs` alone). Only what is read is stored: beats, tempo/key segments, the overview waveform (`wave_minmax_np` / `wave_minmax_ref`, `wave_bands_np` / `wave_bands_ref`, `wave_detail_band_ref`), duration, sr, tempo_global, and the JumpCUE / CUE point / phrase blocks. The editor's save replaces a block as a whole (`core.analysis_library.jobs.save_edits`, its blocks `EDIT_BLOCKS`).
- Track identity across DB, NPZ, thumbnails and playlists is the `uid`; the file path is an editable attribute (`LibraryDB.set_path`; the track panel's Edit tab). `tracks.path` stays UNIQUE (one file, one track).
- `tracks.path` is stored as given, never normalized (case / separators can name different files on other file systems). A path that may spell a library file differently (a drop, External Sync's deck path) is looked up by the file it opens (`LibraryDB.find_file`) and then used as stored.
- A library track whose file is missing is not loaded: the app says so and asks the user for the file's new location (no guessing by name or content).
- `track_tag_sources` (uid, field, slot) holds where the track's file holds its title / artist / album / comment (`core.audio.tag_writer` spellings, as `vorbis:PERFORMER` or `mp4:titl`; one row with source "" when none does: a title from the file name, a field read empty): recorded by the analysis when it reads the tags (`core.audio.track_tags.read_tag_sources`: the spellings holding the values read). The analysis reads the tags and the cover with the app's own readers, no native tag library (an outside file): `tag_writer.read_fields` / `read_picture` for FLAC / MP3 / AAC / WAV / AIFF / MP4 (MediaInfo's order of places, `LEVELS`; the cover the front one, else the first), FFmpeg for the other formats (`decoder.read_metadata` / `read_cover`); the cover is decoded by Qt in the format its first bytes name (JPEG, PNG, GIF, BMP, WebP), at most `COVER_MAX_BYTES`, used by the Export tab's File Tags to write each value back there. BPM and key are not read from the tags (the analysis gives them), so they have no source: they are written to the format's own places. A track without sources (added before they were kept, or given another file: `set_path` clears them) gets them found from its file on its first write.
- Search by Music's index lives apart from library.db in `{libpath}/music_search.db` (`core.library.music_index`): made from the audio alone (all of it dropped and rebuilt when `music_index.METHOD` changes), large (the landmarks, about 130 KB a song), never the user's own. Tables `meta` (the method), `melody` (uid, the file's size / time, the reference lines per frame size), `landmark_song` / `landmark` (hash, song, t; WITHOUT ROWID, clustered by hash). Written by the analysis and by Index Now (Settings > Search > Search by Music: `core.workflows.music_index`: the library tracks not indexed yet, their audio read by up to 4 spawned processes at a lower priority, each entry handed back and stored by the library's owner, the tracks gone from the library dropped; a non-modal progress window as the Rekordbox XML sync's); the search window reads it (a read-only connection the owner lends it) and holds the reference lines in memory.
- Tie-ups (`core.tieup`) live in library.db (the user's own data, made by `LibraryDB.connect` through `core.library.tieups.create_schema`): `tieup_work` (id, category), `tieup_name` (work, name, lang `ll-RR` (a CHECK), type: official / synonym / short / search_hint, is_primary, rank, its readings), `tieup_url` (work, url, label, rank), `tieup` (track_uid, work, role, seq, detail, rank; the key track, work, role, seq; gone with the track). The Tie-ups tab and the Tie-up Works window write them at once (no Apply).
- The Variants' index lives in `{libpath}/variants.db` (`core.library.variants`), as Search by Music's: made from the analysis's features (beats, `wave_bands_np` / `_ref`), never the user's own. Every fingerprint carries its method (`fingerprint.METHOD`: the algorithm and the versions of the features it reads, `analyzer/beat/grid_version.py`'s `BEAT_GRID_VERSION` and `utils/wave.py`'s `WAVE_BANDS_VERSION`: raise them when the tracker's beats or the stored bands change), so a method's change keeps the index: fingerprints are compared only within one method, a track analyzed or indexed gets the current one (Index Now takes the tracks without it), the relations an earlier method found stay meanwhile, and once a track has the current method its earlier fingerprints go (`prune_old_methods`, at Index Now's end); an index made before methods were kept is dropped and made again. Tables `variant_method` (id, name), `variant_song` (id, uid, method, the codes: 5 bytes a frame; one per track and method), `variant_hash` (method, hash, song, frame; WITHOUT ROWID), `variant_pair` (a < b, the method, the relation, b's to a: same / a_instrumental / b_instrumental / vocal, each side's cover, the mix's agreement; `pairs()` the current method's first). A track is stored, then queried against all stored of its method (one writer, the library's owner: of two tracks, the one stored second finds the other); a track stored again (reanalysed) loses its fingerprints and that method's relations first. Written by the library's owner: an analysis's results stored, and Index Now (from each track's NPZ, without its audio). Beatgrid edits do not refresh it (a reanalysis does). A track removed from the library leaves it and Search by Music's index in the same job (`jobs.remove_tracks` -> `jobs.drop_from_indexes`: each a pass over its index); Index Now drops what is left.
- Album art thumbnails (downsampled, JPEG) live in `{libpath}/thumbs/{uid}.jpg` (`core.library.thumbnails`): written by the full analysis, removed with the track; the library table shows the top of each as its first column.
- The key strip is rendered just in time from `key_segments` (`utils.keystrip.render_keystrip`); no image is stored.
- The overview waveform and the main view's preview (its stand-in until the detail chunks are drawn) are rendered just in time from the stored overview (`utils.wave.render_wave_overview` / `render_wave_detail_preview`) in the style of `viewconfig.waveform_style` (RGB, or rekordbox-style 3Band; the overview's bar heights are the bands' power in both, stacked with the 3Band weights: RGB one bar coloured by the band mix against the track's usual balance (`wave.overview_colors`: each column's colour first: each band over its median where the track is audible, so the phrases come out in different colours; cubed, so the band clearly above its usual level leads the colour; red / green / blue for low / mid / high over the strongest as Mixxx's and rekordbox's RGB waveforms; in OKLab one lightness, moved by the brightness: the spectral centroid of the 12 bands against the track's usual one, darker towards the low band's red, brighter towards the high band's blue (a filter sweep inside one range shows); then smoothed in hue over 0.5 s, so it does not flicker: the mean colour's direction and the mean chroma apart, so hues taking turns within a beat never average to grey; the chroma at least the most every hue holds at that lightness; silence neutral), 3Band the bands stacked in their colours; the preview keeps the min / max): low / mid / high are summed from the 12 stored bands with the ranges of Settings > View > Waveform bands (`viewconfig.env_*`, weighted by log-frequency overlap), so a change of the ranges redraws them at once without re-analysis; no image is stored. The detail waveform is rendered from the playback PCM (its three-band scale is the stored `wave_detail_band_ref`).- JumpCUEs are kept in two states in the NPZ: `jump_cues_np` (the user's, replaced by edits) and `jump_cues_auto_np` (the automatic result, replaced only by full analysis or JumpCUE reanalysis). The JumpCUE optimizer (settings → Analysis → CUE) learns from where they differ; do not write edits into `jump_cues_auto_np`.
- A JumpCUE group's colour is a preset index (`graph_color_idx`, presets in `utils/jumpcue_colors.py`), independent of its group number (`graph_id`); no RGB is stored. Edits carry it on each cue as `color_idx`.
- Keys are kept in two states in the NPZ like the JumpCUEs: `key_segments` (the user's, replaced by edits) and `key_segments_auto` (the automatic result, replaced by the full analysis and the editor's whole-track key reanalysis, saved with the editor's next save). The key optimizer learns from the tracks where they differ; do not write edits into `key_segments_auto`.
- CUE points (`cue_points_np`, with a colour preset `cue_color_idx`) are the user's: the full analysis makes them from the phrases by the per-label rules in `config.cuepointconfig` (Settings > Analysis > CUE; LEAD_IN has no rule), after that only the CUE page edits them (phrase edits do not regenerate them), or the Phrase page's CUE button replaces them with what the same rules give the current phrases.
- Phrases cover the track when read: stretches without a stored phrase (all of a track analyzed without phrases) are `UNASSIGNED` (`utils.phrases.fill_unassigned`). It is shown and edited like a label but never stored (`assigned_phrases` on save), so it never reaches training data.
- Phrase labels are the fixed `utils.phrases.PHRASE_LABELS` (no custom labels). How each is shown is a setting (Settings > View > Phrase labels: an alias and an overview abbreviation, empty = the label / its first letter), applied through `utils.phrases.set_phrase_label_names`; stored data always keeps the label itself.
- JumpCUE letters are slots (rekordbox hot cue letters A-Z): the analysis letters them by point; edits keep each cue in the slot the user gave it (no relettering by time). A JumpCUE's user name is its `cue_comment` (equal to its letter = no name). CUE points are rekordbox memory cues: always in time order, no letters; a CUE point's name is its `cue_label`. The Rekordbox XML writes them as memory cues (`POSITION_MARK` `Num="-1"`, with their colours) and the JumpCUEs as hot cues.
- `DataModel` (`core.track.model`) holds the live in-memory track state, its one owner: `features` and `properties` (read-only), `duration_sec`, `album_art`, the predecoded audio, and the marks as edited (`beats`, `tempo_segments`, `key_segments`, `phrases`, `jump_cues`, `cue_points`) with their undo history; changed through its methods alone (above).

## External Sync
- `core.external_sync.ExternalSyncController` follows another program's deck: the track it has loaded and its position, received as OSC over UDP (`OscReceiver`, its own thread keeping each deck's newest state; the GUI takes it at the view's frame rate), one message per deck: `/mixlyzer/deck/time  i deck s path T|F loaded T|F active d|f seconds` or `/mixlyzer/deck/samples  i deck s path T|F loaded T|F active h|i samples i rate` (rate 0: the file's own; a flag may be an i 0 / 1). The deck followed is the lowest-numbered loaded and active one; a deck silent for `STALE_SEC` is gone. Settings > External Sync: on / off, the address and port (127.0.0.1:39321 by default), the status, the message format.
- It listens on this computer only unless the settings name another address; then only library tracks are followed (no analysis started from the network). A path must be a local file: UNC / `//host` spellings refused before and after a link is resolved (opening one sends the user's credentials). Packets are parsed strictly (`core.osc`: lengths checked, only i h f d s T F, 8 KB at most) and refused whole when malformed.
- Mixlyzer reads no other program's memory. The memory reader that used to be here is its own program, the External Sync bridge (github.com/hygn/Mixlyzer_extsync): it reads a DJ program's deck state through the user's pointer chains and sends these messages. The user's chains live in that bridge's git-ignored `bridge.json` and are never committed to either repository (local pre-commit / pre-push hooks refuse them).
- When enabled, local playback/load controls are intentionally restricted.
- If you touch External Sync config or behavior, keep `core/config.py`, `ui/config/`, and `app/window.py` aligned.

## Change Guidelines
- Keep heavy DSP, file IO, and long-running work off the GUI thread.
- The library has one owner, `core.library.service.LibraryService`: library.db, the NPZ files, the thumbnails and the indexes beside them are opened by it alone, all SQL on them is in `core/library/` and every read and write of a `{uid}.npz` in `core/analysis_library/`. Outside them, code names a job (`core.library.jobs`, `core.analysis_library.jobs`) and gets records (`core.library.records`): the GUI `read` / `write` with a ``done`` on the GUI thread, or reads the snapshot; another thread `call`; a worker process is given what it reads (a track's stored analysis included: never its path) and hands back what the owner stores. Never `sqlite3`, `LibraryDB`, `FeatureNPZStore` or another module inside them outside them (`tests/test_library_boundary.py` fails; tests aside). A new operation is a new job in the `jobs.py` of what it is about, with the SQL or file access it needs in the module inside that owns the table or file.
- Worker subprocess entry points must remain module-level pickleable callables. Do not pass Qt objects into multiprocessing workers.
- When changing config shape/defaults:
  - update dataclasses in `core/config.py` (a value playing changes goes to `deckconfig`, deck.json; one the settings dialog sets to the others, config.json),
  - update `default_cfg()`,
  - keep `config.json` / `deck.json` compatibility in mind,
  - update `ui/config/` (only for a value no other place edits: every editable value has one place it is edited),
  - update any call sites assuming the old fields.
- When changing persisted analysis outputs:
  - update readers in `DataModel`/UI/views,
  - update DB segment adapters in `core.linear_segments` if segment schema changes,
  - consider migration needs for existing libraries.
- `library/` is user data. Do not delete, reset, or commit its contents.
- Preserve `uid` linkage between SQLite and NPZ when editing library code.
- Analyzer speed-ups keep every output bit-identical: compare each output array of a few library tracks before and after (in fresh processes, the user's config.json), and replace a loop by a compiled one (numba, with the Python path as fallback) only where it does the same float operations in the same order (the phrase GBM's trees, the downbeat features' small medians).
- Learned models are shipped as `assets/weights/default_<name>` and the settings name the user's `<name>` (missing = the shipped one: resolved by the app through `foundation.model_files.resolve_model`, `core/workers/analysis_settings.py` `model_file`; the analyzer reads the file it is given); every optimizer calls `optimizer.model_start.check_output`, so Reoptimize never writes a shipped file (the phrase and JumpCUE models too), and the spec bundles the `default_` files only.
- Files the app reads may come from elsewhere (audio, models, caches, a library): never pickle (NPZ with `allow_pickle=False`, JSON); a model's arrays are checked before a compiled kernel walks them (`NumpyHistGradientBoostingClassifier._validate`); a length or count read from a file or a command bounds nothing it has not been checked against (the native engine's `ipc::Reader::count`, its PCM block's size); an external program is run by its full path.
- Prefer contiguous NumPy arrays where practical; several rendering and DSP paths assume NumPy-friendly numeric buffers.
- The deck's state is the player's report: a control sends a request and shows `sig_deck_state` / `sig_playback_status`; do not set a transport state in the GUI or the player's worker (the Python engine's `PythonDeck` is that engine's player).
- Keep Qt signal semantics stable. Many slots expect notification-only signals and then read shared model state.
- The loaded track has one owner, `DataModel` (`core.track.model`): its features, properties and marks change through its methods only (a write to `features` raises, its arrays are read-only), and each change is its own signal there. A widget keeps no copy of a mark it edits (it reads the model's); a new edit is a model method or a copy set through one, never a write into `features`. A track change is announced by the model, not the bus.
- A frequent report from another thread to the GUI is the newest value with one queued notification at a time (`core.player._Latest`: the playhead time, the output peak), never a queued signal per value: queued signals are not merged, so they pile up while the GUI is busy and replay stale values after. Progress from a loop is reported when its percent changes. The output buffer stats go every 0.25 s.
- A label whose text changes every frame (a time, a status line) must not ask for a layout each time: fixed in both directions (`setFixedSize`, or a fixed width and height), or a `LiveLabel` when its width follows the layout; plain text when it holds no markup (a rich-text QLabel builds a text document per change).
- If you change view registration or naming, update `views.base.REGISTRY` consumers accordingly.
- A new tool button or action gets a shortcut action: its entry in `ui.shortcuts.ACTIONS`, its handler (`shortcut_handlers` of the part that owns it), and its shipped keys in `assets/shortcuts/default_shortcuts.json` (every action has one; unique, in the tier of what it does, not a system's own: Ctrl+Alt+Del / arrows / F-keys, Ctrl+Alt+L / T (Linux lock screen, terminal), Alt+F2 / F4, Ctrl+Q / W / H (macOS quit, close, hide), Ctrl+Space, Ctrl+Esc, nor a graphics card overlay's: Alt+R / Z, Alt+F1 / F3 / F9 / F10, Ctrl+Alt+R / M, Alt+Shift+R, Shift+F12, F12).
- Every text shown to the user goes through `foundation.i18n.tr()`: placeholders with `.format()` (no f-string inside `tr`), a whole sentence per case rather than words spliced into one (`tr_n` for counts), `tr_mark()` for a module-level table (translate it where it is shown). Logic never reads a displayed text (combo items carry their value as data). `tr` is never a local name (a function binding it cannot call it). After changing texts run `uv run python build/translations.py` and translate the new / fuzzy entries of each catalog.
- Not translated: the main screen's DJ terms (Tempo, Volume, BPM, Key, Bars, the CUE buttons' SET / DEL / MEMORY / JUMP / CALL, the score's accel. / rit.), stored data (phrase labels, cue names, Rekordbox XML), logs, product names. Terms: JumpCUE and CUE point stay as they are (never hot cue / memory cue); the key notation 1A..12B is Alphanumeric (never Camelot); Japanese follows the rekordbox Japanese manual's terms.

- PyInstaller spec is `build/mixlyzer.spec`.
- The spec does not bundle `config.json` (it holds personal settings); the app writes one from `default_cfg()` on first launch. Keep `default_cfg()` free of personal values.
- The spec bundles the shipped assets (`shipped()`: the `default_` models only, icons, the images shown (not the design sources `mixlyzer.psd` / `mixlyzer_large.png`), fonts, sound, style, reading tables, the language catalogs, `default_shortcuts.json`, `default_midi.json`, the native audio engine's `audioengine/native/bin` as built, with VOLK's licence), never a user's file beside them (a retrained model, `assets/shortcuts/shortcuts.json`, `assets/midi/midi.json`). `ffmpeg.exe` is not bundled (its bundling stays commented out): a package's FFmpeg goes into `_internal` by hand, where the decoder looks. `MIXLYZER_CONSOLE=1` builds a console exe (its output and errors readable) for testing.
- In a PyInstaller 6 build the bundled files are in `_internal`, which is `foundation.resource_paths`' root (its module path): every bundled file is read through `resource_path` (never a path from the current folder: fonts, icons, models, catalogs); a settings path (`assets/sound/click.wav`) through `setting_path`, a model's through `foundation.model_files.resolve_model` (as written when found from the current folder, else the bundled file). The current folder (the package folder: `app.main` makes it so) holds `config.json`, the library and the feature caches.
- There is no active `installer/` directory in this repo snapshot; do not document or depend on one unless you add it.

## Safe Assumptions
- Windows, Linux and macOS: code branches on `foundation.os_support`'s flags (the analyzer on `analyzer.runtime`'s, its own), never on `sys.platform` / `os.name` / `platform.system()` itself; a Windows API call has a fallback for the other systems.
- The library format is versioned; old docs that ignore migration are outdated.
- Root `README.md` exists, but localized docs currently live under `docs/`.
